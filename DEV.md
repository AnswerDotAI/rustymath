# Development

## Overview

BPL and rustymath care about two things: speed and simplicity. Before designing a mechanism, study how great software such as tinygrad and JAX solved the same problem. Their authors worked hard to get the foundations right. Let those designs guide ours. Duplicate code, special-case hacks and several paths for similar work are complexity. Find the one principled mechanism. Give each fact one home. The aim is something pure, correct and principled (Jeremy, 30 October 2026). basedpl's `AGENTS.md` states the founding principles.

Rustymath drops precision that numerical code doesn't need, for speed and a smaller implementation. Rustymath doesn't aim for last-bit agreement with other libraries, for reproducible results, or for particular NaN results or signs of zero. The last bits of a result can differ between thread counts, platforms, builds and runs. Only spend speed, memory or code to make them agree if there's a real common practical use case that needs it. Tests never compare results across thread counts.

Keep the documented accuracy bounds that callers use. `nbs/accuracy.qmd` lists every exception in one place. A few ulps more, for real speed or a simpler implementation, become a documented exception there, not a reason to keep slower code. Check a change that alters arithmetic against those contracts, not against bit-identical results. Don't add sign canonicalization, compensated arithmetic or defensive passes without an agreed need. Each shortcut that drops precision is a hypothesis that real uses don't need that precision. When a real use needs digits that a shortcut loses, return that operation to the conservative method, or create an optional parameter.

Rustymath is BPL's mathematics and array core, with a useful thin Python interface over the same algorithms. Generic numerical and array algorithms belong here; parsing, language/function semantics, fusion, JIT, batching and Program construction belong to BPL. Choose ownership by the work an algorithm performs, not by whether BPL currently calls a particular convenience wrapper. Consolidate duplicate general algorithms in rustymath, keeping the better implementation from either project. Rustymath and basedpl have no outside users yet; neither API is treated as published. Discuss public Python removals before making them.

Read `../basedpl/meta/open.md` for the current working host, authoritative source, builds, plans and evidence. Both projects' `meta/` directories stay outside Git.

### Speed measurements

`tests/speed.txt` holds two budgets for each function, in copies of the same number of items: one for macOS on Apple silicon and one for Linux on Syd1. The speed tests compare costs with the budget column that `timing::NATIVE_COLUMN` picks. A `# held` or `# busy` line above the function's line can raise that budget, as basedpl's DEV.md describes. On a platform that checks budgets, a case within 10% of its budget gets a dated `# held` line that raises that column's budget by 10% to allow for noise. Such a hold goes stale under basedpl's rule, once the case costs at most 0.9 times its rule budget. `timing::budgeted` reads a budget file for both speed tests. The speed tests fail for exceeding a budget only on the authoritative CPU, `timing::BUDGET_CPU`: the development Mac's or Syd1's. On any other CPU, the tests print every cost, mark each case still over budget after retries as `over`, and do not fail. An ordinary run times a failing case once more under `timing::try_exclusive`. A calibration run retries it after each pause in `timing::RETRY_PAUSES`: 0.1, 1 and 10 s. `timing::warm` keeps the thread busy for 0.1 s before each retry, because a core that has been idle runs slower at first. Each row also records the instructions retired and bytes allocated per item by its first timed call. `tests/speed.txt` records those counts for each platform. `timing::Count::over` fails a count that exceeds `timing::COUNT_MARGIN` (1.25) times its recorded value. A count changes only when the code does, so counts catch a slower loop on a busy machine too. Only a calibration run times the standard-library comparisons. A cost in copies depends on a CPU's caches as well as its speed. On the 9950X that joined CI's runner pool in October 2026, a 4-byte copy took under a third of the time of an 8-byte one, where the 7950X3D's takes half. 24 of the 28 cases over budget there were f32, though every one of them ran faster than on the 7950X3D. On machines with no budgets, such as Linux on Arm, the speed tests report costs with `budget -`. A copy is the time to negate that many items of the same type and write them into a second buffer, with both buffers in cache. `timing::copy_time` returns this machine's entry in `timing::COPIES`, selected by CPU, item size and number of items. If no entry exists, it measures a copy once and prints a line on standard error for adding the entry. `RUSTYMATH_COSTS` also prints each cost's time per item and a copy line for each item size. A row whose footprint, 65,536 items of its type and the most bytes it holds at once, passes 1 MiB adds that footprint and the time of a copy of it, measured beside the row, as `timing::footprint` describes. basedpl's DEV.md says how the stored times were chosen. The standard-library comparisons are informational. A budget failure often identifies a loop that stopped vectorizing. `RUSTYMATH_COSTS` prints every cost and the comparison table in `src/lib.md`'s "Accuracy and speed".

`tests/test_speed.py` times rustymath's Python API the same way, in the fresh process that `pytest` runs. Its cases are the Python expressions in `tests/speed_python.txt`, each with two budgets in copies of 65,536 items of its section's type, as in `tests/speed.txt`. It reads the file through `rm.timing()`'s `budgets`, which gives each case's `Budget` with its hold and the `Count` that it records for this platform. `RUSTYMATH_COSTS` prints the same copy lines and cost lines as the speed test, through `copy`, `peak_held`, `footprint`, `instructions` and `line`. Its ordinary run holds `rm.timing(shared=True)` and confirms a case over its budget under `rm.try_timing()`. It counts instructions but not allocated bytes, since the Python extension's allocator doesn't count them. To time a change against the build before it, time the baseline build that “Commands and builds” notes and your build with `basedpl.bpltests.pytest_costs`:

```python
pytest_costs(rms, build=base), pytest_costs(rms)
```

Run the existing speed suites locally on the authoritative host. `logged_costs` reads their output. Review repeated costs on the same machine and compare candidate and baseline there. Syd1 thresholds come from released rustymath v0.1.54 measured under `dist`: O3, cross-crate ThinLTO, 16 codegen units, nonincremental. Run `RUSTYMATH_COSTS=1 cargo test --profile dist --test speed`; for Python, run `ship-rs-build --profile dist`, then test the installed wheel with the existing Python speed suite. basedpl uses the same profile, and its own DEV.md gives its native and Node commands. Ordinary `release`/`test` remains the faster-building local-ThinLTO profile. Mac targets and holds are unchanged; never derive ceilings from candidate costs. A budget is a function's expected cost times the multiplier that `set_budgets` applies, as `tests/speed.txt`'s header says. Study costs over budget before deciding whether the code or the estimate needs changing. Set budgets from expected costs with `basedpl.bpltests`:

```python
set_budgets(expected, path=rms/'tests/speed.txt', sections=sections)
```

Here `rms` is this repo's `Path`, `expected` maps each function's name to its expected cost in copies, and `sections` names the item types whose budgets change. `path=rms/'tests/speed_python.txt'` sets the Python cases' budgets. Speed measurements use `parallel::set_threads(1)`. Measure multicore scaling separately.

A calibration run's log also gives each row's counts. `basedpl.bpltests.set_counts` records them in the budget file's column for the platform that ran it.

On macOS, a native timing measures Accelerate wherever the Linear algebra section says Accelerate replaces rustymath's own code. To time rustymath's own versions natively on the Mac, pass `native=True` to basedpl's `time_cases`, `speed_costs`, `cargo_costs` or `pytest_costs`. That sets `RUSTYMATH_NATIVE=1` for the process they time, which dev builds honour. basedpl's wasm build, timed with `speed_costs(wasm=DIR)`, also runs rustymath's own versions. Run the existing native speed suites on Syd1 for x86-64 costs.

Calibration runs of both speed tests, and basedpl's timing tools, take the machine's timing lock exclusively. Ordinary speed test runs take the lock in shared mode and run on one thread. They attempt an exclusive hold only through `try_exclusive`, which never waits. Rust code takes the lock through `rustymath_timing`, whose docs describe its waits and messages. Python code uses `rustymath.timing()` as a `with` block around the same hold, or uses `rustymath.try_timing()`. Shared and exclusive acquisition both fail after 5 minutes; builds and tests never bypass a timing. A thread's nested shared hold reuses its lock file; any nesting involving an exclusive hold fails immediately. Use one lock API for a hold and its nested calls. In a calibration run, both speed tests time each case over its budget again after each pause in `rustymath_timing::RETRY_PAUSES`, and fail only for a case that's over every time. `fastws.timelock` takes the same lock in Python code that doesn't import rustymath, and every rustc call takes it shared through the rustc wrapper that `ws-sync` writes. basedpl's DEV.md lists the builds and tests that take it shared, and the rules for agents.

### Build time and code size

Most of rustymath is generic, so most of its machine code compiles in its callers, chiefly basedpl. Measure a change's effect on build time and code size there, with the tools that basedpl's DEV.md describes under "Codegen and rebuilds":

- Rebuild time: wrap one value in the edited function in `std::hint::black_box`, which changes the generated code but not the behaviour. Time basedpl's `cargo build --lib --bins --release --timings`, then undo the edit and time the rebuild again. The report in basedpl's `target/cargo-timings/` splits each crate's time into frontend and codegen.
- rustymath's own build: `cargo build --lib --release --timings` in this repo times the code that compiles in rustymath itself, such as concrete function forms.
- Build time on other targets: on 28 October 2026, with `pairs_into` and `triples_into` marked `#[inline(always)]`, a `loop-vectorize` pass took about 530 s for x86-64 on each of Γ's and the factorial's f64 slice forms, against seconds for arm64. This crate then took 18 minutes to build for Linux x86-64. With both helpers at plain `#[inline]`, it builds in about 20 s. `CARGO_INCREMENTAL=0 CC_x86_64_unknown_linux_gnu=clang cargo build -p rustymath --lib --release --target x86_64-unknown-linux-gnu --target-dir /tmp/<prefix>_x86 --timings` times this crate for Linux x86-64 as CI builds it. basedpl's DEV.md, under "Codegen and rebuilds", says how to find a function that stalls a build.

A generic function compiles once for each combination of types that callers give it, a conversion closure's type included. Making a loop generic over a conversion as well as its item types multiplies the number of compiled instances. `gather`'s walks show the cost. When their fixed-width row loops took the source type, the result type and the conversion, one basedpl codegen unit held 603 instances of them, about 940 KB of `bpl`, and an edit to them rebuilt basedpl in 16.8 s. With those loops compiled once for each size of item, and conversions in a separate pass (see "Search and gathering"), basedpl's machine code fell by 1.1 MB on 20 October 2026, and the same kind of edit rebuilds basedpl in about 7 s. The fixed-width loops that convert Booleans and integers into `f64` as they write (`Item::cells_from`) add about 17 KB, and leave that rebuild at about 7 s.

## Code map

The dependency layers are `rustymath-core` → `rustymath-kernels` → the public `rustymath` facade; the facade also uses core directly. Core owns formulas, number facts, storage and geometry, without depending on executable kernels. Kernels owns concrete typed execution. The facade explicitly exports math/array capabilities, scalar formulas and their public traits/macros; kernel-only helpers stay in the lower crates. BPL owns language evaluation, Program/trace/fusion/JIT policy and diagnostic labels. Files below are relative to `core/src/` unless qualified.

## Functions, formulas and kernels

Free functions are generic over `Float`: f16 computes in f32 and rounds its result, while f32 and f64 use their own working type. `Native` names f32 and f64. `functions!` declares the free wrappers at the crate root and in `fused`/`unfused`; an `as` entry also declares the formula object. `FUSED` selects hardware FMA where available. Don't introduce software FMA into targets without it.

`facts::Formula<N>` owns each object's supported dtypes, numerical bodies, validity, ranges, reductions and partial derivatives. `Kernel::resolve` selects a computing dtype and result dtype for known formula objects; `Kernel::of` selects from a runtime `Op`. `Kernel::{real,integers,complex,exact}` evaluates scalars. `map`, folds, scans, writes and products use the same resolved definition over `Read` plans. `Variant` selects checked or wrapping arithmetic. `Settings` supplies the execution tolerance outside item loops.

`Formula::native_slices` supplies optional typed bulk callbacks in `NativeSlices`. Kernels choose them at the map boundary and otherwise run the formula's item body. Keep specialized logarithm, power/root, error-function, complex-comparison and distribution routines behind this table. A native callback writes every result slot even when its verdict reports failure. Real and integer callbacks return a Boolean verdict; complex callbacks leave the final validity check to the map boundary. f16 arguments widen to f32 at that boundary.

`Formula::emit_valid` and `FAILS_NAN` define checked formula failures; IEEE NaNs are valid results for arithmetic that accepts them. `Kernel::may_raise_on` bounds those failures from argument ranges. BPL uses that query to admit deferred calls. Native bulk loops retain `Outcome` and `Total` for their verdicts: plain floating results fail on a new NaN, `Option` fails on `None`, a wrapped-result pair carries a fit flag, and `Total` never fails. Test the chosen formula or native verdict rather than imposing one NaN rule on every function.

Tolerant formula objects retain their declared tolerance. A kernel's `Settings` overrides it for the execution. Native bulk routines select exact or tolerant implementations once per call through `with_tolerance!`.

### Loops and codegen

`appended` reserves spare capacity without zeroing it; `written` views initialized slots for later passes. Kernel outputs use `MapOutput`, `Output` and `parallel::Slots` to write allocated or caller-provided storage. Those helpers centralize storage initialization and the associated safety checks.

`each` runs the ordinary item loop. It checks outputs first and inspects arguments only for NaN outputs. `two_pass` computes a branch-free fast path, then recomputes its rare misses. `CHUNK` governs cache-sized pieces in native bulk routines and conversion adapters.

In two loops that ANDed a compound flag for each item, x86-64's loop vectorizer left the loop scalar, where arm64's vectorized it. On CI's x86-64 runner in October 2026, the log-normal density took about 2.5 times as long per item, and `3|v` about 3.7 times. `distribution.rs`'s `composed` flagged `!r.is_nan() | v.is_nan()` in its `finish` loop. `each`'s loops flag only `!r.is_nan()` and check `kept` afterwards for NaN results. These loops vectorize on both targets, and `composed` now uses the same pattern. The exact `Residue` flagged `!far(x, y)`, whose `x != 0` test shares its comparison with the residue's own `x == 0` select. x86-64 kept that select as a branch. Its loop now flags `near(x, y)`, which leaves out the test of `x`, and vectorizes on both targets, with 3% fewer instructions for `3|v` on arm64. `two_pass!` also vectorized it, but its NaN select and NaN check cost arm64 21% more instructions for `3|v`. basedpl's `bpl-tests disasm --x86` shows whether a loop vectorized.

These measured loop patterns are useful starting points; their reasons matter more than preserving a particular implementation:

- Prefer `each!` or `two_pass!` for item bodies where they fit. They mark closures `#[inline(always)]`; leaving a large body out of line can stop vectorization.
- Separate closures can move runtime function selection outside the item loop. A shared closure can leave the selector inside every iteration. `trig.rs` shows the pattern.
- `pairs` currently uses `#[inline(never)]` because inlining a loop behind `parallel::split`'s `&dyn` repeated its setup at every call site. Revisit the choice if the calling structure or measurements change.
- Measure a generic change in its basedpl caller as well as the small Rust test crate when compilation context can affect the result.
- Filling a large per-call buffer through `appended`'s spare capacity, or `Vec::with_capacity` and `resize` as `linalg`'s `filled` does, avoids a measured macOS calloc cost. `vec![0; n]` uses calloc there; its `madvise` cost exceeded writing the items and grew with the number of threads touching the buffer.
- Plain slice loops with representations chosen before the loop, or calls to small `#[inline]` helpers, have avoided per-item dispatch and cross-unit calls in measured hot paths. Local builds of the `test` profile are incremental, in up to 256 codegen units, with thin LTO across each crate's units. In an incremental build, a generic function without `#[inline]` gets one copy per crate, in one unit. std's iterator plumbing, such as `Map::fold` and `Vec`'s `spec_extend`, has no `#[inline]`. Thin LTO inlines such a copy into a caller in another unit only when the copy is below LLVM's import limit of 100 instructions. A longer one, such as a fused iterator `fold` over several adapters, stays out of line, and the loop runs as calls, sometimes one for each item. Which unit holds a copy changes with unrelated edits. A default trait method called on a concrete type also stays out of line unless it has `#[inline]`. CI builds the `test` profile with `CARGO_INCREMENTAL=0`. Its builds split code into units differently from local builds. A loop through `Steps::offsets` also runs `get`'s variant match and reloads its fields for every item, because the compiler can't rule out that the output buffer aliases the `Steps`. In basedpl, `BASEDPL_CALLS=pattern cargo test --test units -- --nocapture` lists each call from a matching function into another unit, in basedpl's build and in the rustymath rlib it links.
    - `Steps::offsets` currently maps a `Range` through `get` to produce a `TrustedLen` iterator. `Vec::extend` and `zip` use their fast loops only for `TrustedLen` iterators, and stable Rust doesn't let a new type implement `TrustedLen`. Replacing it with a custom iterator increased the cost of a write such as `x.[i]←w` from about 9 copies to 21. A hot loop over a table loops over its slice directly.
    - Moving 64-bit integer multiplies outside vector loops helps NEON, which has no 64-bit vector multiply. Multiplying each table entry by a stride as it was read stopped `Steps::combined`'s loop vectorizing, and a write such as `x.[i]←w` cost about a copy more. A table holds finished offsets, which `Table::scaled` multiplies once.
    - `Steps::for_each` matches the kind of step once before its loop, avoiding a measured call per row. LLVM can keep `get` out of line despite its `#[inline]`, even within the caller's unit. A loop over rows through `get` or `offsets` then makes a call for each row. Before `for_each`, each short row cost about 3.5 ns in `scatter_into` and `walk_into`: `[∞;0 1]⌷m` on 65,536 rows of 4 floats cost 15 copies, against 2.2 with it.

Elementary kernels aim for branch-free vectorizable loops. Incomplete gamma/beta and their inverses also use data-dependent series, continued fractions and iterations, with precision-appropriate stopping. Table gathers help AVX2 but are unavailable in NEON/wasm. Short dependency chains and vectorizable conversions matter as much as instruction count.

`Pow`/`Root` use table-based f64 arithmetic and narrow-width vector paths. Their scalar formulas have separate fast paths; f32 scalar calls use tables that the vector paths avoid. For an integer exponent from 2 to 8, `Pow` uses squaring and multiplication in both the scalar form and the slice form with a constant exponent. For a degree of 2 or 3, `Root` uses `sqrt` or `cbrt`. A table-free f64 `Pow` measured about 30% slower: with `ln` and `exp` in one loop, their polynomial constants don't fit in registers. The loop then rebuilds them for every item. `cbrt` computes at each width's own precision. Trig slice forms redo large arguments after their fast reduction. f64 inverse-error slice forms group inputs by approximation region. `Erfc` chooses a single formula for blocks wholly on one side of its split. Normal/log-normal bulk CDF and quantile routines reuse those optimized loops through `composed`.

### Parallel execution

`parallel::ranges` schedules independent ranges. `split` applies it to disjoint output slices; `pairs` and `extended` use that interface. A long call times its first unit, then cuts the rest into pieces of at least `PIECE_TIME` of work, at most four for each thread. When there are fewer pieces than threads, `pieces` uses a pool whose size is the largest power of two no greater than the number of pieces. Memory-bound calls of a million items ran faster on small pools than on all 18 threads of an M5 Max. Chunked forms keep their temporary buffers in cache. Work and result initialization finish for every piece even if another piece reports failure. `parallel::extended` lets a caller such as basedpl's fusion fill a vector's spare capacity in pieces, through `Slots`.

`parallel::stack` runs a function on each cell of a stack of matrices, for basedpl's `f⍤2` and the binding's matrix functions. Each cell writes its part of each of the stack's outputs, a tuple of one to three `Vec`s (`parallel::Outputs`), as `Stacked::qr` writes Q and R and `Stacked::svd` U, S and V. `parallel::each` gives a result of any type for each cell. Both schedule cells through `each_cell`, which times the first cells on the calling thread, then splits the rest across threads in rounds of about `ROUND_TIME` for each thread, with an interrupt check between rounds and one scratch value, such as an `LuWork` or `QrWork`, for each piece. A cell on another thread doesn't split again.

The default pool follows `RAYON_NUM_THREADS`, otherwise Rayon's available-core default. `parallel::set_threads(n)` changes the number for the whole process and returns the previous setting. Use 0 to restore the default or 1 for serial calls. Calls already on a Rayon worker do not split again. Wasm runs serially. Pools are created on demand and rebuilt in a child after `fork`.

This scheduler covers elementwise forms, folds and matrix products. Scans don't split. `reduce::along` folds each lane, or group of `inner` lanes, whole if it fits in one piece of `reduce::fold_pieces`. It splits runs of these lanes or groups across threads. Larger arrays fold in one piece per thread, each of at least 2^18 items and 16 rows. A lane that crosses pieces merges its parts' folds on the calling thread. A wide array splits by rows this way where it has enough rows to give each thread a piece of 16 rows. With fewer rows, `along` splits its columns, in units of at least 2^18 items, and each thread reads part of every row. `along`'s doc comment gives the timings behind this choice. A fused fold produces its items in contiguous ranges, so it can split only by rows. A product splits its rows into bands of about `BAND_WORK` multiply-adds, each with its own packed block of `a`. It splits once for each panel of `b` of up to `PANEL` items, or `SERIAL_PANEL` bytes when it runs on one thread, across at most √(work / `THREAD_WORK`) threads. Each thread it wakes costs about as much as `THREAD_WORK` multiply-adds. Decompositions split in the products of their blocked updates. The Hermitian and bidiagonal reductions also cut each pass's rows into one piece per thread, each of at least `ROW_PIECE` rows, through `eigen::summed_rows`. Divide and conquer splits each merge's secular roots, corrected z and vector rows. Panels and the recursion's two halves run on one thread. Callers that submit only small converted chunks also limit the work available to run in parallel. The shared non-generic scheduler keeps Rayon's machinery out of each kernel instantiation. Item types and forms are `Send + Sync` through the sealed traits.

## Other numerical modules

### Reductions

`Reduction` defines the unit, scalar step, checked step, contiguous fold, merge and scan for `Sum`, `Product`, `Max` and `Min`. Integer sums/products wrap and report whether they fit. f16 sums and products have an f32 `Total` on every fold path, column folds and `fold_pieces` merges included. The caller rounds it once. f16 extrema total in f16. Float sums/products can regroup algebraic operations. In any route that folds by a float maximum or minimum, repeated writes through `Combine` kernels included, a NaN item must never cause a non-NaN extreme read before it to be discarded. The route's code may skip NaN items or pass NaN on to the result, whichever the target's fastest instruction does. Callers can rely only on NaN or the extreme of the items that aren't NaN: the maximum of 5, NaN and 3 can be 5 or NaN, never 3. Today every target's code skips NaN items, as the docs of `Max` and `Folds` describe. The maximum of NaN items alone is therefore `-∞`, and their minimum `∞`.

`slice::running` chooses the partial-total count for the target and item size. Explicit vector extrema are used where they outperform ordinary loops. On AArch64 and in wasm, f32 running sums scan four-lane vectors through `sum_scan`, which makes `+\` about 1.3 times faster than `grouped`'s groups of four items. Float folds and scans use AArch64's `fmaxnm`/`fminnm` and wasm's `pmax`/`pmin`, one instruction each. AArch64's scans read each item as it is, because `fmaxnm` drops a NaN on either side. Elsewhere a NaN running result stays NaN, so a scan turns each NaN item into `-∞` or `∞` as it reads it. `Folds`' defaults, which x86-64 runs, read each item through a step from `-∞` or `∞`, one instruction there. Wasm tests for NaN and selects, because LLVM compiles that step to two comparisons, an `or` and a select. The test made wasm's `⌈\` and `⌊\` on rising or falling items about 1.2 times faster. A scan's seed is its first running result. Wasm's `max`/`min` give NaN beside NaN and take about eight instructions each on x86-64 hosts. Integer extrema scans skip blocks that cannot change their running result.

`Logical` holds a Boolean dyad as a truth table and scans by composing its two-state maps. The Boolean reductions (`Max`/`Or`, `Min`/`And`, `Xor`, `Xnor`) scan through it. `scan_along` runs their lanes of at most 64 consecutive items in one call of `mapped`, which restarts each lane inside its word (`Reduction::short_lanes`). `SumAs<C>` counts Booleans or sums integers in the caller's chosen total type. The caller must choose a width that holds the totals.

`Alternating` implements right folds by subtraction or division. Float/complex pairs sum differences or multiply ratios. Integer subtraction keeps separate totals for even and odd positions. A floating quotient reports failure when its intermediate products or result leave the normal range; basedpl then folds item by item.

`along`, `scan_along` and `fold_into` traverse `[outer, len, inner]` arrays. Contiguous lanes of at least `SHORT_LANE` items use slice reductions, and shorter ones fold item by item. Along another axis, rows no wider than `slice::running`'s running-total count are folded in blocks of whole rows, with one running total per item in the block. Each column's totals then merge. Wider rows are folded four rows at a time into blocks of 64 KB of totals. The totals stay in the first-level cache, and each row's items are read in order. Folding each strip of columns down every row in registers reads consecutive items a row apart. On arrays larger than the cache they took about 4 to 6 times as long as a fold along the last axis. `fold_into` accepts blocks from callers such as fusion. `extremes` and `extremes_of` compute both bounds in one pass. `along_mapped` folds an array described by a mapping over storage without building the array. Where the mapping reads a block of storage, as `Mapping::block` finds, `Block::fold` gives the dimensions to fold the block along in its own order, and the tables that read the totals in the array's order. Other mappings fold each run of at least `RUN` items where it lies, and copy shorter runs a piece at a time. `rereads_cheaply` says whether a mapping folds with no copy at all. When `rereads_cheaply` is false, a caller that will read an array again keeps a compact copy, as basedpl does for a pending copy that a name holds. `RUN`'s doc gives the measurements behind it.

`sliding` folds each window of `width` rows along the middle axis of an `[outer, len, inner]` array. Windows of up to `DIRECT` rows fold directly, one pass for each row. Wider windows use van Herk-Gil-Werman's method: each window folds one block's suffix with the next block's prefix, so the cost per item does not grow with the window width. For lanes of single items, one const parameter compiles each loop over a row to scalar code and keeps the running fold in a register. A running sum, recomputed every 1,024 windows, ran float sums two to three times faster on the Mac. The running sum's error grows with every item processed since it was recomputed, rather than only with the items in the current window. A spike of 1e20 among ones then makes subsequent window sums zero until the running sum is recomputed. Sums therefore use van Herk-Gil-Werman's method too. `picks` returns the row of the first item that attains each window's, lane's or running fold's maximum or minimum. Windows run `sliding` over pairs of an item and its row. `view_picks` runs it at a view's own type, for basedpl's `⌈` and `⌊` rules and the Python `sliding_argmax` and `sliding_argmin`. `kernels!(Sliding of r)` runs `sliding` at each dtype, for the Python `sliding` and for Python folds of views of windows. `structure::Slide` classifies a copy of windows from its walk (`Walk`) as sliding folds over the copy's source: the source items to read, the rows to fold, and the tables through which the copy's other axes read the folds. basedpl folds its pending copies of windows through it. For a Python view, which holds only its storage, `walked_source` gives the row-major source shape that the view's strides imply.

### Complex functions and distributions

Complex functions live in `complex.rs`. The facts table's complex formulas call them, so kernels run them on each item. `Abs` and `Angle` are formula objects for complex magnitude and angle. Exceptional magnitudes and branch-cut cases take their own paths inside each function. Inverse circle/hyperbolic functions use Kahan's formulas; complex ln Gamma uses Stirling, recurrence and reflection with SciPy's branch convention.

Complex errors are measured against a magnitude-based scale, with function-specific scales for ln Gamma, powers, Gamma and binomial. Quarter-turn directions are deliberately exact. See `complex.rs` for that contract rather than applying a separate ulp bound to each component.

`Distribution` validates parameters and holds a `Law`. `Pdf`, `Cdf` and `Quantile` are formula objects whose native bulk callbacks select the law outside their item loops. Each law gives its density, cdf and quantile as slice forms, its `_many` methods, which by default run a map that holds its constants in a loop. `Pdf`, `Cdf` and `Quantile` call those slice forms even for a single item. `Quantile` gives NaN for a p outside 0 to 1 before any law's formulas run (`quantiles`). The closed-form laws, normal, log-normal, uniform, exponential, Cauchy, Laplace, logistic and Weibull, use f32 working arithmetic for f32 inputs, with parameters and precomputed coefficients narrowed before the item loop. Other laws use f64 arithmetic and narrow their outputs. A closed-form law takes `erfc`, `erfcinv`, `ln`, `log1p`, `atan`, `tan`, `pow` and `root` from their slice forms through `composed`, because those functions vectorize in their slice forms but not inline in a law's loop. The Weibull law takes its powers from `Pow` and its quantile's root from `Root`, which keep its cdf and quantile within 4 ulps where e^(shape·ln z) didn't. Branches in a formula select between values computed beforehand. A division or an `exp` inside one arm of a branch keeps the loop scalar. The accuracy page lists the cases past 4 ulps, and `closed_forms_at_f32` in `tests/numeric.rs` checks the f32 forms against f64 to a relative error of 1e-4. Sampling, rolls and deals take a caller-owned RNG. Keep RNG ownership separate from the numerical algorithms.

### Integers, exact numbers and polynomials

`Overflowing` gives wrapped integer operations and fit flags without branching in the hot loops. Integer kernels (`recipe::IntegerOps`) and folds run them, and `Pow`'s integer forms give the pair as their outcome. Every reduction wraps too. A result that doesn't fit fails, with the wrapped result in its slot. The Python API keeps that result, as NumPy does. BPL's exact integers widen instead. `Width::float` and `DType::inexact` take the widest float that an integer may become: `f64` for NumPy's rule, or a session's narrower default float. `DType::common` uses the float or complex dtype when combining it with an integer dtype, as JAX does; NumPy instead widens the float. `convert::int`/`float` use bit-based conversions where target instructions do not vectorize. Check `NATIVE_64` and `SATURATING` before replacing them with casts. `Divisor` turns repeated division by one integer into multiplication and shifts.

`integer` provides checked gcd, lcm, binomial and power functions. `residue` returns an integer directly, including the dividend for a zero divisor. Objects also have narrow and unsigned forms. `encode`/`decode` handle mixed radix; polynomial decoding handles fields.

`number_theory::Natural` narrows BigUint through u128 to u64 before computing. The fixed-width tiers use Montgomery arithmetic; BigUint uses ordinary residues. Pass cancellation checks by value through narrowing calls. Passing `&mut check` recursively creates new closure types and unbounded monomorphization. `Primes` is a segmented wheel sieve.

`exact` operates on rational numerators/denominators. `linalg::exact` supplies row reduction, solve, pseudoinverse and determinant for fields; least-norm solves use a rank factorization. Permanent uses Ryser's Gray-code formula. Basedpl uses rational matrix solves/determinants and native floating decompositions for approximate inputs. Generic permanent and polynomial helpers also run on f64 and complex floats. Long-running functions check for an interrupt between steps.

`polynomial` provides generic `value`, `factored`, `from_roots` and `derivative`, vectorized Horner evaluation, companion-matrix roots and least-squares fitting. Keep Horner's blocks fixed-size: variable slices can introduce copies and iterator setup in downstream codegen. Measure changes in basedpl too.

### Search and gathering

`search` owns exact search, classification, counts, interval index, stable counting/radix sorting and grouped positions. Positions are u32; slices must fit that range. Whole-slice algorithms stay out of line to avoid duplicating them in callers. Each buffer of a `Grouped`'s `Groups` holds whole classes, which `grouped_keys` writes in one pass over table keys. Two classes take a buffer each, which `into_buffers` hands over without a copy. More classes share one buffer, because a buffer for each class costs an allocation that callers reading only the positions don't need. A fold of each class reads `Numbered`'s class numbers in one pass, with no positions built; `Numbered::counts` counts them only where a caller needs the sizes.

`hashing` is the one home for hash maps and sets, in rustymath and basedpl both. Its `Hashing` is foldhash's fast `RandomState` with `hash_one` marked `#[inline(always)]`, because hashbrown 0.17 hashes through core's default `BuildHasher::hash_one`, which incremental builds called out of line on every lookup. That call made tolerant `v⍳w` about a fifth slower. `HashMapExt` and `HashSetExt` give `new` and `with_capacity`, which hashbrown has only for its default hasher.

Sorting, partitioning, rank selection and quantiles share exact ordering keys. Float ordering treats signed zeros as equal and puts NaNs last in ascending order. Partial selection leaves unrequested ranks unordered. Median and quantiles select their required ranks without a full sort.

`tolerant` owns relative comparisons, rounding and tolerant searches. Search can index whole-number keys, but validates returned matches unless the haystack is exactly whole and falls back to buckets when needed. Classification intentionally permits tolerant chaining and whole-key groups; it is not the same relation as matching every member against a representative. `Near` and `runs` implement the non-whole paths. Tolerance-sensitive tests need independent inside/outside cases and exact controls.

`gather` copies through a caller's conversion for cycle, repeat, indexed take and scatter. `positions` lists the positions a mask sets: it skips blocks of 64 counts that are all 0 and writes blocks that are all 1 in one loop. In a mixed block, it and the split into two classes in `search` write only the selected items through the 8-bit `SET` table. `walk` copies the items that one `Steps` per axis reaches: strides, clipped ranges, rotations and offset tables. Build a clipped range with `Steps::clipped` and a rotation with `Steps::rotated`. Each returns a `Stride` when no clipping or wrapping is needed. Every `Clipped` entry reads at least one fill. Every `Rotated` entry wraps. Positions outside the source take the caller's fill. `walk` merges neighbouring runs, copies long runs whole, transposes through `linalg::transpose_into`'s tiles and writes short windows through `windows`. `scatter_walk` writes through the same fast paths: transposed tiles, reversed and strided runs, index values converted inside the write loop (`Table::put_into`, as `Table::take_into` reads them), and cells at a table of starts (`placed`, as `picked` reads them). `walk` and `scatter_walk` take a `Convert`. With `Same`, they move items straight between source and result. A walk with `Same` of at least `SPLIT` items splits across threads in whole `CHUNK`s, through `parallel::extended`, unless the calling thread's calls run serially. Each thread walks its range a `CHUNK` at a time into a buffer of its own, then copies the buffer into its part of the result. On 4 threads, the walk runs about 1.5 to 2 times as fast. Memory bandwidth limits the gain, as does the requirement that `parallel::ranges` give each piece at least `PIECE_TIME` of work. Any other conversion runs as a separate pass over blocks of about `CHUNK` items: a walk gathers a block of source items, then converts it, and a scatter converts a block of items, then writes it. Their walks therefore compile once for each item type (`Item`), and their fixed-width loops, `windows` and `windows_into`, once for each `Unit`: an unsigned integer, or an array of two, with an item type's size and alignment. Two slice casts, `units` and `written_as`, move items as units. Both casts are sound by the promises of two unsafe traits. An `Item` type has no padding and has its `Unit`'s size and alignment, which `units!` checks at compile time. Every bit pattern of a `Unit` is a value of it, so items read as units are valid units. `written_as` writes only units that `units` read from items of the same type, so each slot it fills holds a valid item. That matters for `bool` and `char`, which have bit patterns that aren't values. A conversion's own pass costs about 0.25 ns per item on this Mac, measured on 20 October 2026. A conversion inside the walk cost nothing extra, because the walk waits on memory. To avoid that extra pass, `scatter_walk` uses fixed-width loops that convert Booleans and integers to `f64` while writing short cells along a stride through `Item::cells_from`. `units!` provides those loops only for the five Boolean and integer source types. They add about 17 KB of basedpl's machine code. `Steps::through` composes two walks into one only where the result stays regular, or where either walk is already an offset table. Elsewhere callers walk the inner copy into a buffer first. Walking the inner copy into a buffer costs one pass, whereas building and reading a table of every offset costs two. Basedpl reuses these paths for structural operations. Measure search/gather changes there as well.

`agreement` pairs two layouts by BPL's broadcasting rule. `Agreement` is generic over its layout type, which BPL uses to retain its renderer. `Mapping` describes positions as `Single`, `Linear`, `Tiled` or `Steps`; it carries no fill value. `ReadPlan` names source inputs and their logical lengths, maps, joins, index values and default or invalid positions. Maps compose through `ReadPlan::remapped`, retaining their missing-position plan. `Missing::Scalar` reads a separate one-item source, and `Missing::Input` supplies another plan. `Binding::full` binds a whole source; `Binding::window` binds a range within its producer's logical extent. A kernel reads the bound sources through `Read`. `Read::part` borrows contiguous or repeated items where possible and copies other requested ranges into typed scratch; `part_view` lends a contiguous run at its storage dtype or fills a scratch buffer. `ReadPlan::runs` exposes source, fill, index and invalid runs, and `RunSink::walk` accepts a structural walk whole. The retained `Walked` helpers also serve mapped linear-algebra and reduction paths: `in_place`, `copied`, `tiled_cycle` and `copy_walked`. `Mapping::{entries,tables,to_walk}` exposes positional geometry without data or fill conversion.

### Optimization

`optimize` has four entry points: `minimize` takes an `Objective`, and `solve`, `solve_linear` and `solve_affine` take a `Mapping`. An objective gives a value, a gradient where `has_gradient` says it has one, and a batch of values in one call through `values` where `batch` says it evaluates batches. Without `batch`, `Search` calls `value` on each point of a batch. A mapping writes its values into a slice, gives vector–Jacobian products where `has_vjp` says it can, and gives its Jacobian through `jacobian`. By default `jacobian` builds the rows from vector–Jacobian products when the mapping has no more values than variables, and otherwise leaves Levenberg–Marquardt to forward differences. Where `has_preconditioner` says it has one, its `precondition` gives `solve_linear` a preconditioner. A solve without one uses each residual as it is, with no copy. Each optional method has a flag beside it and an unreachable default. An override therefore implements only the case that its flag enables. A closure that returns a `Result` is an objective or a mapping, and `Differentiable` pairs a value closure with its derivative. The closure's error type becomes the entry point's error type. A caller's interrupt or failed call therefore stops the search without a separate check, which matters because basedpl's and Python's functions can fail on any evaluation.

Every method of `minimize` and `solve` runs on a private `Search`. `Search` counts evaluations against the limit. Before evaluating a point, it moves the point inside the bounds in the method's own buffer. It treats NaN as +∞ and keeps the best point. A method returns whether its stopping test passed. Running out of evaluations unwinds through `Halt::Spent`, and `passed` then gives `converged` false for the best point. `solve` wraps its mapping in `Norm`, an objective whose value is the norm of the residuals, and which keeps the residuals for the method to read. `solve` and `solve_affine` take `first`, the mapping's values at the start, which give the number of residuals. The caller computes them, because only an evaluation tells a binding how many there are. `Search::seed` counts that evaluation and records it, and the methods start from it, so it isn't repeated. Bounds, the limit, NaN and the result therefore live in one place for minimizing and solving, and a new method should run on a `Search` too.

One line search serves Brent's method and Powell's. `least_along` brackets a minimum with golden-ratio steps, which stop at the bounds' limits along the line, and `brent` searches the bracket. Brent's method is one such line search along its variable. Every Nelder–Mead move puts the worst vertex at a point on the line from the centroid of the others through it, with Gao and Han's coefficients for the number of variables. L-BFGS uses `linalg`'s `axpy` and `dot`. Differential evolution evaluates each generation through one `values` call, which lets basedpl evaluate a generation as one array, and then polishes its best point with Powell's method. Its generator is `random::SplitMix64`, seeded from `Options::seed`, which the truncated SVD's test matrix also uses.

`root` finds a zero of one equation in one variable, from finite bounds as its bracket or by stepping outward from the start. Levenberg–Marquardt solves each damped step through `linalg::lstsq` on the stacked matrix [J; √λ D], where D holds each variable's largest Jacobian column norm so far. `lstsq` keeps the step accurate where JᵀJ would square J's condition number.

`solve_linear` runs CG, MINRES and restarted GMRES through `Products`. It counts products against the limit, and for least squares it applies AᵀA as one product with A and one with Aᵀ. `Task::least_squares` decides when a system is least squares. Calls to `Mapping::precondition` do not count against the product limit. Each method's doc comment gives its stopping test. `solve_linear` reports the true ‖b − A x‖ from one more product. MINRES and GMRES build their plane rotations through `linalg`'s `givens`, which the tridiagonal and bidiagonal iterations also use. `solve_affine` passes `solve_linear` an `Affine` mapping, which computes each product from the values of an affine residual, as (f(t v) − f(0)) ÷ t. Its doc comment says how it picks t.

basedpl's `⇄` and the Python binding share `Task`, `Method::choose`'s default policy, `Options::check`'s rules for options that a front rejects, and `Method::NAMES`, the methods' names. Every tolerance is relative, with an absolute floor near the tolerance squared. On Rosenbrock's function from (-1.2, 1), Nelder–Mead took 364 evaluations, Powell's method 423, differential evolution 1767 including its polish, and L-BFGS 53, each ending within 10⁻⁸ of the minimum.

## Linear algebra

`Inner<T>` objects compile matrix products in rustymath. On macOS 15+, Accelerate computes float and complex plus-times products. Elsewhere the native `product` blocks for caches and calls register micro-kernels, with explicit vectors on supported AArch64, AVX2/FMA and wasm SIMD targets. A product with a vector, where the result has one row or one column, goes to `by_vector` on every target, because packing would copy the whole matrix and pad the vector to a tile. Where Accelerate serves the process, `by_vector` takes only matrices whose stored rows hold at most `NARROW` (8) items, because Accelerate pays a fixed cost for each stored row. On an M5 Max (30 October 2026), a 65536×8 f64 matrix times a vector took 216 ps a multiply-add on Accelerate against 88 in `by_vector`, and a vector times it 102 against 77. From 16 items a row, Accelerate was 1.3 to 7 times as fast as rustymath's own kernels. Where the matrix's stored rows run along the contraction, each result is the sum of products of a stored row with the vector: rows of 8 items two at a time, whose sums add pairwise in one vector step (`narrow_dots`), and other rows four at a time (`dots`). Otherwise each result reads one item of every stored row. At most 8 results keep their sums in registers across every stored row, in four sets that each take every fourth row (`narrow_sums`). More results add into strips of 32 results in registers, 8 stored rows at a time, which reads each block of rows in storage order. Results that don't fill a strip of 32 take strips of 8, then one at a time. On an M5 Max, the cost of a 1024×256 f64 product fell from 290 to 500 ps per multiply-add to 88 to 94 ps, compared with 74 ps for one read of the matrix. `by_vector` splits results across threads. If all results fit in one strip, it instead splits the stored rows, with each piece accumulating into its own results. `by_vector` reads the vector in place when its items are adjacent and need no conjugation. It writes directly into the output when the results need no scaling, conjugation or step. `tiles` owns target tile sizes. Integer products select a narrower exact kernel when their bounds permit it. `Wrapped<PlusTimes>` multiplies `u8`, `i16` and `i32` matrices with wrapping steps at `i32`, as static kinds and fixed widths keep integer results, and `Product::run_wrapped` runs it. Where every sum fits `f32` exactly, `u8` and `i16` items compute in `f32`, as `i64` products do. Where Accelerate serves the product, a sum that fits `f64` exactly computes in `f64`. Every other product runs on the `i32` kernel, which every target compiles, because Accelerate has no integer product. On 512×512 `u8` matrices, Accelerate's `f64` product took one fifth of the `i32` kernel's time, while rustymath's own `f64` product took 1.6 times as long. `PlusTimes` at f16 sums in f32 and gives f32 results. rustymath's own kernels convert each f16 item to f32 as they pack it, so neither operand is copied whole. Where Accelerate serves the product, both operands convert to f32 copies for its f32 product, because Accelerate has no f16 product. `Inner::checked_into` writes a product into its slot of an output, or gives `false` where an integer result doesn't fit. `linalg::Product` represents a pair of operations for code that chooses the pair at run time. `Product::run` selects the pair's kernel for the arguments' dtype through `Kernels::product`. Python's `inner` and basedpl's `pervasive::inner` both take it. A count computes at `i64` or a float, because a narrower count can overflow. Boolean products use packed bits, and equality-count products use kernels appropriate to their item width. `Inner::inner_mapped` takes operands whose items an `agreement::Mapping` reads, as a pending copy in basedpl holds them. Its default reads each operand whole. In `blocked`, float and complex `PlusTimes` use an operand where it lies when its mapping reads it at positive strides with one stride 1, as a strided or transposed matrix. They read any other operand a block of its stored rows at a time and multiply each block as it's read. Where that operand's rows are the result's rows, and the product runs on one thread or the other operand has at most `PIECE_MATRIX` items, each thread multiplies its own piece of the result's rows, in blocks of at least `BLOCK_ITEMS` items. Each thread's product packs its own copy of the other operand, and with several threads larger copies crowd the cache that the threads share. Otherwise an operand of up to `WHOLE_ITEMS` items is read whole, and a larger one in blocks of at least that many, each gathered across threads and multiplied in one threaded call. Rows along the contraction add into the result (`contracted`), through a copy of the result for each thread where it holds at most `BLOCK_ITEMS` items. A product with a vector, whose other operand's rows are adjacent in storage in runs of at least 64, as the windows of a vector or a single-channel image are, goes to `by_columns`. It adds each column of that operand, read where it lies and scaled by its item of the vector, into the result. With 4 or more columns, or runs of 3 or 16 rows, gemm over gathered blocks measured faster. Python's `matmul`, and `inner` with `add` and `multiply`, call it for a float or complex view where `Mapped::in_place` says gemm reads both operands where they lie. They copy any other view first, such as reversed rows, because `blocked` was still slower than one copy and one gemm in two cases (28 October 2026): a product with a small `b` on 18 threads of rustymath's own kernels, and an operand above `WHOLE_ITEMS` with threads. `signal::correlation` provides read plans for a correlation or convolution: the array padded according to the mode, its windows, and the kernel. For convolution, the kernel is reversed. `signal::correlate` runs them through `inner_mapped`, which builds no windows matrix for float and complex `PlusTimes`. Python's `correlate` and `convolve` use it for sums of products of floats and complex numbers. Other pairs and dtypes gather the windows matrix and call the same product as `inner`.

One private `Matrix` view and `Tiled`'s `multiply`, `gemm`, lower-triangle `gram` and in-place `triangular` serve public products and decompositions. Views carry leading dimensions and transpose/conjugate operations. `Tiled` also holds each item type's dense drivers, `svd`, `eigh` and `eig`, behind fronts in `factor.rs` that handle nonfinite and empty matrices. On macOS, `accelerate.rs` serves all of these, apart from complex `eig` and the decompositions of small matrices, from one table of BLAS (GEMM, SYRK/HERK, TRSM) and LAPACK (GESDD, SYEVD/HEEVD) symbols, plus a real-only GEEV table, through the ILP64 interface, which takes any size. Complex `eig` uses the native solver on every target, because Accelerate's ZGEEV and CGEEV took 2.4 and 2.9 times as long. Real `eig` takes GEEV from `accelerate::GEEV_FROM` (256) rows, and the native solver below that, which was 1.2 to 2.7 times as fast up to 128. The SVD takes GESDD from `GESDD_FROM` (24) rows and the Hermitian problem HEEVD from `HEEVD_FROM` (65), because Accelerate's fixed cost for each call made the native solvers faster on smaller matrices. `from_order!` makes these three choices. `build.rs` sets the `accelerate` cfg on macOS, and the `native` cfg wherever rustymath's own kernels compile: on other targets, and on macOS with the `native` feature. `native` is a default feature. Dev builds keep it. Mac release builds turn it off with `--no-default-features`. Dependent crates, such as `rustymath-py`, depend with `default-features = false` and make `native` their own default. The native packed plus-times products and triangular solves compile only where `native` holds. Where both compile, `dispatch!` uses Accelerate for them unless `RUSTYMATH_NATIVE=1` selects rustymath's own kernels for the whole process. `accelerated()` reports whether Accelerate or rustymath's own kernels serve the process. LAPACK reads a row-major matrix as its column-major transpose. GESDD factors a tall matrix through its adjoint, because Accelerate's GESDD took nine times as long on a 4096×16 matrix that it saw as wide. HEEVD reads the lower triangle as its upper one. GEEV takes a column-major copy. Every LAPACK working copy takes its leading dimension from `stride`. Without padding, a 512×512 matrix took twice as long in GEEV as a 511×511 or 513×513 matrix, 27% longer in GESDD and 8% longer in SYEVD. Each thread's BLAS setting follows rustymath's thread setting. It is single-threaded when `parallel::serial()` holds, including on batch worker threads and after `set_threads(1)`; otherwise, Accelerate uses its own threads. It changes only when that choice does. NumPy's calls into Accelerate on the same thread use the same setting. Rustymath needs macOS 15 at run time, for Accelerate's `BLASSetThreading`. Its `pyproject.toml` gives the wheels that minimum. Cargo never reads a dependency's `.cargo/config.toml`. A crate that ships a binary must therefore set `MACOSX_DEPLOYMENT_TARGET=15.0` in its own `.cargo/config.toml`, as basedpl does. Without it, the binary still links but records Rust's default minimum, 11.0.

`Scalar` and `Factor` cover f32, f64 and complex numbers with f32 or f64 parts. `Scalar::Real` is the type of singular values and Hermitian eigenvalues. Scalar method names avoid clashes with float traits. Complex division uses scaled Smith arithmetic; public `divide` keeps its faster, narrower-range formula. Native complex products form each part from two real products of the parts, as scalar multiplication does. Accelerate uses complex GEMM directly. Nonfinite complex products need not match scalar arithmetic. Singular/eigenvector signs and phases are not canonicalized.

`linalg/factor.rs` owns LU, Cholesky, QR and their solves. LU factors a column-major copy of the whole matrix in place. `Lu` keeps the factors in that layout. `lu_panel` halves the columns until `LEAF` or fewer remain. It factors the left half, applies its row swaps to the right half across threads through `swap_rows`, updates the right half through substitution and a packed product, then factors the right half. LU's solves go through `triangular`. When the process uses Accelerate, LU's inverse solves from the permuted identity. With rustymath's own kernels, it solves from the identity and skips the zeros above the diagonal of `L⁻¹`. Cholesky works in blocks of `cholesky_block` columns. Trailing updates and blocked triangular solves use packed products. QR stores Householder blocks in WY form; one `Block::apply` serves QR updates, Q construction and applying Q or its adjoint. QR factors each block of `qr_width` columns through `panel_qr`, which halves the block and updates the right half and T through products. `Block::new` builds T for the eigen and SVD blocks through the same halving. LU, Cholesky and QR work in copies whose rows, or LU's columns, lie `stride(n)` items apart. `stride` adds 8 items to a length that's a multiple of 128, which keeps a power-of-two size from mapping every row to the same cache sets. LU and Cholesky remove the padding before returning, leaving their rows or columns `n` items apart. Cholesky reads only the lower triangle. Thin `qr` and `lstsq` of a tall matrix first try `tall_qr`, CholeskyQR2 with a partial Gram matrix for each thread, above the cutoff in `tall_for_qr`. The cutoff admits the sizes where it measured faster on one thread, and larger sizes where its threaded passes are faster on the default thread count. Where Accelerate runs the products, the larger sizes are admitted on one thread too. There, 1000000×10 is about 3 times as fast as Householder. Elsewhere they're admitted only where the call can split across threads. Wasm and `set_threads(1)` calls use Householder for them. `tall_qr` falls back to Householder when a Cholesky factor fails or `Q₁ᴴQ₁` is far from I. For tall or square matrices, `lstsq` reduces `b` to `Qᴴ b` without storing Q, then solves through R's SVD. Wide matrices solve through their SVD directly.

`solve` and `pinv` use LU when the square matrix's pivots pass the scale-dependent eligibility check. Otherwise they use the least-norm SVD path. The SVD cutoff is shared with `rank`; LU applies no singular-value cutoff. Consequently `rank` can be smaller than the dimensions used by a successful LU solve. Keep this distinction rather than forcing both routes to agree at a rank boundary. `Lu` supplies solves, inverse, factors, determinant and log-determinant. `Lu` and `Svd` are generic over their storage: `LuRef` and `SvdRef` are the borrowed forms, which `new` builds from slices and `as_ref` gives from an owned factorization, with the same methods. `qr_complete` forms full Q.

The native SVD, Hermitian and general solvers compile everywhere. `factor/eigen.rs` reduces Hermitian matrices to real tridiagonal form. It reads only the lower triangle. Small vector problems use implicit QL; larger ones use divide and conquer with deflation and secular roots. Reconstructing the secular update from the roots maintains orthogonality. Values-only calls omit rotations of eigenvectors. `factor/general.rs` reduces to Hessenberg/Schur form and back-substitutes eigenvectors: real matrices use Francis double shifts, complex matrices use single shifts. Padding avoids cache-set conflicts in column reads. Eigen routines return `None` on failure. GEEV balances and permutes first, so on macOS a real triangular matrix of `GEEV_FROM` or more rows needn't give its eigenvalues in diagonal order.

`factor/svd.rs` reduces to a real bidiagonal problem. Small vector problems use Golub-Kahan QR; larger ones use divide and conquer. Values-only calls use QR at every size without constructing or rotating singular vectors. Tall matrices first reduce to R, through `tall_qr` where `qr` or `lstsq` would use it. Power-of-two normalization protects the shift/rotation arithmetic. `factor/truncated.rs` holds `truncated_svd`, which runs on every target: it approximates the leading singular values and vectors with a randomized range finder from a fixed seed, through products, thin QR factorizations and one small SVD. Nonfinite input or nonconvergence gives NaN outputs. Pseudoinverse forms the scaled vector product directly. Source constants own block widths and algorithm cutoffs; test their boundaries through the hidden exports rather than duplicating values in tests. Tests compare a scaled matrix's singular values, Hermitian eigenvalues and least-squares solutions with the unscaled ones to rounding, because LAPACK's internal scaling isn't a power of two. Scaling can change the signs, phases and order of singular vectors and eigenvectors. Tests check the scaled matrix's vectors through their own residuals and orthogonality or unit length. They check its general eigenvalues through their sum, which must equal the trace.

## Python boundary

Expose useful mathematical and array capabilities through a thin Python interface to the shared Rust algorithms. A public Rust helper does not require a matching Python binding. Keep Python argument decoding, defaults, scalar-return policy and result wrappers in `py/src/` or `python/rustymath/`. Keep generic mathematics and array algorithms in rustymath even when a Python convenience is their only direct caller. Related bindings share the core's names, argument order and dtypes. A function with NumPy's name needn't behave as NumPy's does. `remainder` and `floor_divide` round through the comparison tolerance where one is set, set functions keep first-occurrence order, orderings put NaN last, and `diagonal` and `trace` take the last two axes, as the matrix functions do.

Python operations are eager. `python/rustymath/create.py` gives fill constructors their names/defaults over one native fill primitive, and names the dtype facts that Rust returns. Sequence generation stays in `create`. Structural functions and bracket indexing in `py/src/structure.rs` delegate selector decoding to `buffer/src/selection.rs`, shared with BasedPL, for the selection and writeback paths. Bracket indexing uses `structure::plan_parts`, the planner shared with BasedPL's `⌷`. Index arrays pair by broadcasting, as in BasedPL's `.[]`, using arithmetic's rule for names. A selector with one axis name selects along the axis with that name (`structure::addressed`). Every selection remains a view of shared sources, including index arrays and padding (`Array::selected`). `reshape` keeps a view's mapping, which reads the same items in order under any layout. Readers borrow runs they can use in place and gather other requested ranges into scratch storage. A view keeps its `ReadPlan` and source buffers, without a materialization cache. `take`, `pad` and `windows` read positions past an end by `structure::Edge`'s modes, which BasedPL's `•edge` names: `take` through `Edge::positions`, and `pad` and padded windows through `Steps::padded`. `structure::Windows` plans windows for `windows` as it does for BasedPL's `↕`. A `fill=` is checked at the array's dtype through `Buffer::kept` and retained as a separate one-item source, selected by `Missing::Scalar`. Assignment detaches shared storage, preserving independent values. `rm.at` combines through the same selection with `Array::combine_at` and its function's `Scatter` kernels, sharing `Array::assign`'s checks. A view retains its whole base until `compact()` copies its logical items, even when it is a contiguous subrange. Methods call the same binding functions as package-level operations. `python/rustymath/structure.py` composes conveniences such as trace and repeated differences. Differences run subtraction kernels on two mappings of the input, not gathered copies. `python/rustymath/random.py` subclasses the native generator for distribution conveniences and multivariate-normal sampling. `py/src/random.rs` owns its RNG. Sampling, rolls and deals stay in the shared core.

`py/src/array.rs` holds `rustymath.Array`, which wraps a rustymath `array::Array`. `numpy.asarray` receives a read-only snapshot through `rustymath_buffer::export`. Each export pins its exact backing allocation and signed-stride geometry until `__releasebuffer__`, independently of later assignment to the Python owner. `rm.array(x)` shares existing rustymath storage with independent values and copies foreign inputs. `py/src/convert.rs` retains the call's ownership, scalar classification and NEP-50 promotion policy. Its arguments expose core `ArrayView`s. Dense callers prepare once through core `Items`. Elementwise callers keep their mappings. Arrays of different dtypes promote through `DType::common`. Nested lists, tuples, `range`, `dict` and `str` follow the same converter. `None` is read as NaN when it is an item. A bare `None` doesn't convert, so an operator given one returns `NotImplemented`. A pandas `DataFrame` reads through `rustymath_buffer::frame`: its columns convert together, as a list of them would, and transpose into a matrix of rows by columns keyed by its labels. `rustymath_buffer::labels` is the one rule for a dict's keys and a frame's column labels, shared with BasedPL. `give` returns a rank-0 result as a Python number when every data argument was a Python scalar. `rustymath_buffer::read_array` reads sibling snapshots with keys and names. The shared buffer reader normalizes signed bytes, wider unsigned integers and foreign byte order, borrows contiguous aligned items, and uses CPython's `PyBuffer_ToContiguous` to copy other layouts into C order. It doesn't use PyO3's `PyUntypedBuffer`, which rejects rank-0 exports. The crate has no Rust tests, because PyO3's `extension-module` feature unifies across the workspace, and a test that embeds Python can't link. `tests/test_array.py` tests it through the class.

`py/src/functions.rs` holds the elementwise functions, reductions and scans, one entry each in the `functions!` and `reductions!` macros. A function converts its data arguments through `convert`, finds its object's kernels with `kernels!`, and runs them at the dtype that `Kernels::computes` gives. `convert` promotes the arrays' dtypes with `DType::common`. It then applies `DType::common_weak` for the Python values, as NEP 50 does for weak scalars. BPL shares both rules. When an argument's dtype has no kernel, `Kernels` casts it to the first dtype that has one: `int64`, then `float64`, then `complex128` for Booleans and integers, and a wider float, then a complex dtype at least as wide, for floats. The object's slice form then reads the items in place and splits independent ranges across threads, as it does for Rust callers. `checked` converts a kernel's result into the call's result. It returns the `missing` error for an unsupported dtype. When `Kernels::wraps` says the kernel wrote a wrapped integer result, it returns that result, as NumPy does. Any other integer result that doesn't fit its dtype raises `OverflowError`. Comparisons, and the functions that round or divide through them, take one scalar `ct`. Where `ct` is None, `functions::tolerance` reads the process's tolerance, which `set_tolerance` sets and which starts at 0, exact. The Rust core takes every tolerance as an argument, so the setting lives in the binding, and BPL's own tolerance setting never changes Python's results. A tolerance of 0 runs the exact algorithms, through `Exactly` (`with_tolerance!`).

With no `axis`, a reduction reduces the whole array and gives a Python number, and a scan runs over the flattened array. Reductions take axis positions, names or tuples of them. `accumulate(f, x, axis=None, start=None)` scans any native binary function from the left, with an optional scalar seed. The same `functions!` entries supply its callbacks and `inner`'s. Known reductions retain their optimized scans. Comparisons keep the computing dtype, reading later results as 0 or 1. A sort, `argsort` or `lexsort`, takes one axis and works along the last axis by default. Grading shares native-width key construction and stable sorting with BPL, including heterogeneous lexsort keys. Folds and scans call `Kernel::fold_read` and `Kernel::scan` over shared `Read` plans. The kernel selects accumulation dtypes and reads or converts each requested block through those plans. `minmax` over the whole array takes `reduce::extremes`' single pass for Booleans and integers, and two folds otherwise. `logical_scan` takes a 2×2 truth table.

Statistical bindings in `py/src/functions.rs` share conversion and axis preparation through `stats::Axes`. Numerical loops live in `stats`, including two-pass variance, weighted averages, covariance and histogram counting. Float16 statistics accumulate and return float32. The 2-norm folds through `reduce::Squares`, which computes and sums the squares in float64, for float32 data too, with no buffer of squares. `linalg::norm`'s Frobenius norm is that 2-norm over every item. Complex variance and norms return real values.

`linalg::Stacked` (`src/linalg/stacked.rs`) runs rustymath's matrix functions on stacks of matrices, for rustymath's Python API and basedpl alike. A call computes in the dtype that the ladder (`DType::computes_in`) gives the common dtype of all its array arguments, singular values included, so no argument narrows. Exact numbers compute as floats of the width that the caller passes to `Stacked::new`: rustymath's Python API passes `DType::numpy_float`'s, float32 for Booleans, `uint8` and `int16` and float64 for `int32` and `int64`, and basedpl passes its exact width. Results take the common dtype where it's a float or complex dtype, and the computing float otherwise, so float16 computes in float32 and gives float16 results. `rustymath::agreement::Frames` pairs the arguments' frames, the axes before each argument's cell, by rustymath's broadcasting rule. It gives each argument's cell for each cell of the result. `linalg::cells` runs a function on each cell of the result through `parallel::each`, with scratch such as an `LuWork` for each thread, and an interrupt check between rounds. A function whose results are slices writes each cell straight into its outputs through `parallel::stack`. `linalg::paired` reads a right-hand side so that its rows pair with the matrix's rows by key, and `linalg::stored` lays a result out as the frame's axes, then the cell's. A right-hand side of one axis is one vector. Row positions read as index positions do (`structure::signed_positions`), so a float position must be a whole number.

`py/src/linalg.rs` wraps each of `Stacked`'s methods: it converts the call's arguments, runs the method with the GIL released, and gives the results. Every binding uses `convert::released` to release the GIL during computation. Module initialization installs `convert::signals` as the interrupt check through `rustymath::interrupt::install`. `convert::signals` acquires the GIL to check for Ctrl-C only on a thread running computation through `released`. Rustymath's worker threads and calls that hold the GIL pass without taking it. Two bindings hold the GIL throughout: `optimize.rs`, which calls a Python objective on each step, and `Array.__setitem__`, whose mutable borrow would otherwise make another thread's conversion of the same array fail. A call reads each `rustymath.Array` argument as it was when converted, because the argument shares the array's storage and a write copies shared storage before changing it. A Python thread that writes to the items of a buffer argument, such as a NumPy array, during a call leaves the call's results undefined, as NumPy's are.

Singular values and Hermitian eigenvalues take the real dtype of the matrices' width. General eigenvalues and eigenvectors take the complex dtype. Row positions and ranks are int64. A matrix that a decomposition can't factor gives NaN results, with no report. `lu` returns the packed factors in rustymath's own order, where row `j` holds column `j`. `lu_solve`, `lu_inverse`, `lu_det` and `lu_slogdet` read them in place. `lu_lower` and `lu_upper` build the separate triangular matrices that `Lu.l` and `Lu.u` give. `product` shares frame and keyed-axis preparation for `matmul` and `inner(f, g)`. Recognized pairs, which the `products` and `boolean_products` sections of the `facts!` table name, keep their specialized kernels. A count of floats or complex numbers within a tolerance takes the generic route instead, because the count kernels compare exactly (`Product::compares_exactly`). Other native pairs call `linalg::inner_with` per cell through `linalg::cells`, then join the results. The existing `functions!` entries generate their bulk binary and right-fold callbacks; no Python callbacks run inside a contraction. Empty contractions use existing reduction units or raise when none is known. Integer products raise `OverflowError` for a result that doesn't fit int64. `python/rustymath/linalg.py` names the functions and builds the `Lu`, `Svd`, `Eigen` and `Echelon` results, whose methods call the Rust functions. Preserve the intentional API differences: `svd` returns V, not NumPy's V-adjoint, and complete QR is selected with `complete=True`.

`py/src/exact.rs` reads integers, Fractions, nested lists of them and integer buffers through `rustymath_buffer::walk`, the walker that `convert.rs` and basedpl's Python import also use, computes with BigRational, and returns Fractions, in nested lists for arrays. Its elementwise functions broadcast through `Agreement`, and its matrix functions check their own shapes, so `python/rustymath/exact.py` only names the functions. Exact matrix calls take one matrix, and `solve` takes a vector or a matrix as its right-hand side. The ordinary linalg module also exposes permanent and 2-D row reduction. Both row-reduction APIs return `Echelon(rows, pivots, determinant)`.

The remaining binding files match their Python modules. The polynomial functions compute in float64 for Booleans and integers, and in float32 for float16, rounding the result back. Integer mixed-radix conversion checks int64 overflow. Number theory takes Python integers through BigUint and polls for Ctrl-C. The search functions sort, find insertion positions, classify and group through the `search` module's functions on views, which basedpl's searches also call. `search.py` adds the `Unique` tuple and `bins`, and the package root reexports the search functions. Sorts compare exactly, equate signed zeros and put NaNs last. Distribution constructors live in a submodule, so their names don't collide with the elementwise functions'.

`with rm.explain() as report:` captures native routes from every worker thread through `events.rs`. `report.routes` lists successful routes. `report.records` contains aggregate `kind`, `route`, `reason`, `calls` and `items` records. A report displays its records, one a line. BPL uses the same capture implementation in its own native module. Nested captures include their records in the outer report. A process supports one active capture except for nesting on one thread.

`py/src/optimize.rs` runs `rustymath::optimize` on Python functions, and `python/rustymath/optimize.py` gives it SciPy's names: `minimize`, `root_scalar`, `least_squares`, and the linear solvers `cg`, `minres`, `gmres`, `cgls` and `lsmr`. Each returns a named tuple: `OptimizeResult`, `RootResults`, `LeastSquaresResult` or `LinearResult`. The module stays out of the package root, where `root` is the nth-root ufunc. A float32 or float16 start, or `b` for the linear solvers, computes in float32, and anything else in float64. Each evaluation checks for Ctrl-C, then calls the Python function with a rustymath array. `read` uses the shared converter to read the Python function's result in row-major order, casting its items to the search's float type. A function can therefore return any shape, such as a 2-D Jacobian. An exception from the function stops the search. The wrapper turns SciPy's `bounds` pairs and its `maxfev`, `popsize` and `seed` options into the binding's arguments. The binding's first call of `least_squares`'s `fun`, at `x0`, gives the number of residuals and becomes the search's first evaluation. `least_squares`'s `jac` gives `Vectors::jacobian` the whole Jacobian in place of vector–Jacobian products. The linear solvers take a matrix, whose products `Product` computes in Rust through `PlusTimes.inner_ops`, or anything with a `shape` and a `matvec`, as SciPy's `LinearOperator` has. `cgls` and `lsmr` use the transpose, through `rmatvec` or the matrix, because the core solves least squares for any matrix with a transpose. `M` takes the same forms and becomes the core's preconditioner. Our `gmres` applies `M` on the right, where SciPy's applies it on the left. SciPy's `lsmr` takes no `M`. `maxiter` keeps SciPy's meaning, iterations or GMRES's restart cycles, and `linear_at` converts it to the core's limit on products. `Options::check` and `Method`'s `FromStr` give the argument errors, so the binding repeats none of the core's rules. With `vectorized`, the function gets points as the columns of a 2-D array, as SciPy's `differential_evolution` passes them.

`lib.rs` adds each module's functions, and `set_threads`, `thread_setting`, `threads`, `set_tolerance` and `tolerance`, to the extension module.
