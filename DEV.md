# Development

## Commands

```bash
cargo test
RUSTYMATH_COSTS=1 cargo test --test speed -- --nocapture
cargo develop && pytest -q
nbdev-test
nbdev-preview
ship-rs-build
```

`cargo test` runs the accuracy tests, the speed test and the doc examples, in about a second. Run plain `cargo test` while you work. Build nothing else without explicit discussion first, such as scratch crates, `--release` builds, other target directories, `-p` builds or builds for other targets. `tests/speed.rs` times each function at f64 and at f32, in copies of the same number of items, and fails when one goes over its budget in `tests/speed.txt`. A loop that stops vectorizing takes several times as long and goes over budget. With `RUSTYMATH_COSTS` set, the test prints the README's table, which compares each function with the standard library's version where it has one, then each cost as a line such as `f64 Exp: 7.22, budget 15`. The `Speed` workflow prints the same on CI's runner. It runs only when started by hand. After a `Speed` run, `set_budgets(native=[cargo_costs(rms), logged_costs(log)], run=run, path=rms/'tests/speed.txt')`, from `basedpl.bpltests`, sets every budget under the rule in the file's header. Here `rms` is this repo's directory as a `Path`, `log` the `Speed` job's log and `run` its run number. `cargo_costs` runs the speed test on this machine. The `Test` workflow, in `test.yml`, runs the `test` job on each push to main and each pull request. It and the `Speed` workflow run on Ubicloud's `ubicloud-standard-4` runner. The budgets come from that runner. The `Speed` workflow restores the cache that the `test` job saves. The `Release` workflow, in `ci.yml`, runs only on a `v*` tag, on GitHub's runners. It runs no tests, because the tagged commit's tests ran when it was pushed. It builds the wheels and the sdist. Once the builds pass, it publishes the crate to crates.io. It publishes the wheels and the sdist to PyPI and attaches them to the GitHub release.

Timings and builds keep apart through a lock on `/tmp/aai-ws-timing.lock`, which rustymath and basedpl share. The speed test takes it exclusively, as basedpl's timing tools do. `cargo develop`, basedpl's `cargo wasm` and basedpl's `pytest` take it shared. A timing waits while anything else holds the lock. Anything else waits while a timing holds it. Each waits up to 5 minutes. After that a timing fails. A build goes ahead without the lock. On macOS, the speed test also sets its thread's QoS class to user-interactive. macOS then keeps the thread on the performance cores. The operating system releases the lock when its process ends, even by a crash.

## Layout

The root package is a pure Rust crate, published to crates.io. Rust users who depend on it never build PyO3. The Python extension is the `py` package. It depends on the root crate, is never published, and maturin builds it through `[tool.maturin].manifest-path`.

`py/src/lib.rs` makes each function a NumPy ufunc. A ufunc's loops cover float16, float32 and float64, complex64 and complex128 where the function object has complex forms, every integer type where NumPy's function takes integers, and `bool` where NumPy's keeps Booleans. The Boolean loop comes first, then the integer loops from narrowest to widest, signed before unsigned, because NumPy picks the first loop whose types its inputs cast to safely. Each loop runs the object's slice form through the `Kernel` adapter on `CHUNK` items at a time: an input with stride 0 becomes `Arg::One`, a strided input is copied into a buffer, and each chunk's results are copied into NumPy's output. `ufuncs!` lists the ufuncs, each with its kernel type, how to make it, and its loop groups. `remainder` runs `Residue` through `Flipped`, which puts its arguments in NumPy's order. `add` and `multiply` run rustymath's `Add` and `Multiply`, and `maximum` and `minimum` run the objects `reduce::Maximum` and `reduce::Minimum`. On Booleans, `add` and `multiply` run `reduce::Maximum` and `reduce::Minimum`. `maximum` and `minimum` fold through `rustymath::reduce` for `reduce` and `accumulate`, and so do `add` and `multiply` on floats, `i64` and `u64`, ignoring whether an integer fold fits, because it wraps. Booleans fold and scan through `reduce::Max` and `reduce::Min`. NumPy sums and multiplies narrower integers at `int64` for `reduce`, because it upcasts by the ufunc's name. NumPy calls a loop for `reduce` and `accumulate` with the output as the first input, and `run` recognises those calls: other ufuncs then step one item at a time. Each loop clears the floating-point status flags that branch-free code sets in discarded lanes, then raises "invalid value" for a NaN from arguments that aren't NaN, or "overflow" for an integer that doesn't fit, so NumPy reports them through `numpy.errstate`. The tolerant ufuncs take the tolerance as an extra input and read its first item. The wrappers in `python/rustymath/__init__.py` check it and pass it. `py/src/search.rs` exposes rustymath's searches, exact through `search` for Booleans and integers, and tolerant through `tolerant` for floats. `unique` in `__init__.py` takes its first positions, class numbers and counts from `search::numbered`. `index` and `isin` shape `index_of`'s positions as NumPy does.

The other modules have one file each in `py/src/`. `polynomial.rs` takes contiguous arrays of one dtype, which the wrappers in `python/rustymath/polynomial.py` prepare, following the conventions of `numpy.polynomial.polynomial`. `number_theory.rs` and `distribution.rs` become the submodules `_core.number_theory` and `_core.distribution`, which `__init__.py` also registers as `rustymath.number_theory` and `rustymath.distribution`. They're submodules because the distribution constructor `gamma` and the ufunc `gamma` can't share a module. The number theory functions take Python integers through `BigUint`, and check for Ctrl-C through `Python::check_signals`.

`linalg.rs` makes rustymath's decompositions and matrix products generalized ufuncs, in the submodule `_core.linalg`. `register` makes a generalized ufunc from a signature, such as `"(m,n),(m,k)->(n,k)"`. NumPy gives each of its loops whole core matrices, with their strides. Each generalized ufunc has loops at float16, float32, float64, complex64 and complex128, and the `gufuncs!` entry for each one lists the type of each argument: the loop's element type, or the real or complex type of the same width. Singular values, a Hermitian matrix's eigenvalues and `slogdet`'s logarithm have the real type, `eig`'s results the complex type, and `lu`'s row positions and `rank` the int64 type. The max-plus and min-plus products have no complex loops. A loop copies each matrix into a row-major buffer in its working type, `f32` for float16, calls rustymath, then writes the results through the output's strides. A signature can't name the smaller of two dimensions. A function whose results have `min(m, n)` rows or items, such as `qr`, therefore registers twice with one loop: `qr_m` for matrices with no more rows than columns, and `qr_n` for the rest. A matrix that fails, such as one that `cholesky` can't factor, gets NaN results and raises "invalid value", which NumPy reports as it does for a failing item of any ufunc. `solve` and `pinv` call rustymath's functions of those names, which give a result for every matrix. The wrappers in `python/rustymath/linalg.py` choose the generalized ufunc, convert integers and Booleans to float64, and treat a one-dimensional `b` as one right-hand side. Each takes the name of NumPy's similar function, with the arguments and results of the Rust function it wraps: `svd` gives V, where NumPy gives Vᴴ, and `qr(a, complete=True)` calls `qr_complete`.

## Functions

Each free function is scalar Rust, generic over `Float`, with no branch on its usual path except where this section says. The compiler inlines it into the loop that calls it, such as a function object's slice form, and vectorizes that loop. `lib.rs` declares every function once in `functions!`, which also puts it in the modules `fused` and `unfused`. `mla` fuses its multiply and add only where the target has FMA (`FUSED`). A software `fma` in wasm would stop the loop vectorizing. Code compiled with FMA for itself calls `fused`. `pow`, `root` and `cbrt`, `pow`'s core, and `table.rs`'s logarithm and exponential carry `#[inline(always)]`. LLVM would otherwise leave them out of line, and the loops that call them would stop vectorizing. The `tolerant` module holds APL's tolerant comparison.

LLVM vectorizes a loop that reads a table only where the target has gathers, as AVX2 does. NEON and wasm have none, so on Apple silicon such a loop runs one item at a time, even with unchecked indexing. LLVM keeps the constants that don't fit in vector registers in general registers and copies one in for each use on every iteration, so each distinct constant costs an instruction per pass. A long chain of dependent operations limits a loop as much as its instruction count does: Estrin's form for a polynomial, or z² beside b z in place of b z z z, shortens the chain. `cargo rustc --profile test --test speed -- --emit asm` writes the speed test's assembly to `target/debug/deps/speed-*.s`, one file per codegen unit.

At f64, `pow` and `root` use `table.rs`: Arm Optimized Routines' logarithm and exponential, with tables of 1/c, ln c and 2^(j/256), and double words (`dd.rs`). At f32 and f16 they compute e^(y ln |x|) in f64 with no table, so that their loops vectorize everywhere. `ln_narrow` and `exp_narrow` serve those widths, and the special functions' narrow paths, with polynomials that keep only the accuracy a narrower result needs. `pow.rs`'s `fast` computes a power or root that needs no special case: a positive, finite, nonzero base, a finite exponent, and at f64 a product within `table::NORMAL`. At f64 it uses `table::ln_normal` and `exp_normal`, which leave out the selects for special values and the exponential's two-factor scaling. The slice forms run `fast` through `two_pass`. `pow_any` and `root_any` handle every argument with no branch, with special values tested at the argument's own width, after the result narrows. Testing them at f64 converted each mask between f64 and f32 lanes and cost f32 `pow` about a quarter of its time.

`Pow`'s and `Root`'s scalar forms compute one value per call, which no loop around them can vectorize. Their `forms!` calls in `pow.rs` use `pow_one` and `root_one`, which take one branch to a fast path wherever it applies, as Arm's scalar `pow` and `powf` do. At f64 the fast path is `fast`. At f32 and f16 it is `fast_single`, which reads `table.rs`'s port of Arm's scalar `powf`: `log2_single` with a 16-entry table and `exp2_single` with a 32-entry one. Those two load their polynomials through `loaded`. LLVM otherwise builds each constant on every call from four moves and a transfer between registers. The free functions `pow` and `root`, which a caller's loop inlines, take that branch only at f64, where their loop reads tables anyway, and stay branch-free at f32 and f16. `cbrt` takes its first estimate from the bits of x and needs no table.

`lambertw` sums Corless et al.'s series in p = √(2(ex + 1)) below p = 1/2, near the branch point at -1/e. Elsewhere two steps of Fritsch's iteration refine a first estimate, with no table. A step's error is about `ln`'s error times |w| / (1 + w), and the series reaches far enough from the branch point to keep it within 2 ulps. ex + 1 cancels near the branch point, so ex comes through a double word. Narrower types compute in f64. Complex W0 runs Halley steps from the first estimates SciPy uses, each step divided through by e^w so that its parts stay near |w|.

At f64, `erfinv` and `erfcinv` take one branch to one of six regions of Boost.Math's rational approximations, with no iteration. On uniform arguments, mispredictions of that branch took half the time. The f64 slice forms of `Erfinv` and `Erfcinv` therefore place each block of 512 items by region without a branch, then run each region's formula over its items. The normal and log-normal `Quantile` objects take erfcinv(2p) from `Erfcinv`'s slice form. f32 and f16 take Giles's single-precision approximation.

Conversions between floats and integers go through a float's bits wherever the target has no vector instruction for them. AVX2 and wasm have none between `f64` and 64-bit integers. `convert::NATIVE_64` names the targets that do. `Core::from_low` turns a whole number below 2^m into a float. `Core::to_low` turns it back. `SHIFT` + x holds a signed whole number x, as `pow2` and `flip` read it. `convert` gives the public conversions on the same bits. A narrow integer converts from a float after a range check. On x86-64 it then converts through `to_int_unchecked`, because Rust's saturating `as` compiles to one scalar conversion per item on AVX2. Elsewhere it converts with `as`, because AArch64 and wasm saturate in vector form, and wasm's unchecked conversion runs one item at a time. `convert::SATURATING` names those targets. The check is one comparison, of the distance from the middle of the type's range. With two comparisons, NEON's f32 loop ran out of registers and spilled.

`src/accuracy.rs` checks every function, with `mla` fused and unfused, at every f16 input, at samples of f32 and f64 inputs and at the cases in `testdata/`. Every check must be within `BOUND`, 4 ulps. The elementary functions are checked against the platform's libm through Rust's standard library, except `asinh`, `acosh` and `atanh`, which the standard library computes with formulas of its own and the tests call from libm directly. Rounded to f32 or f16, libm's f64 result is a correctly rounded reference. At f64 a check against libm allows `LIBM`, 2 ulps more, for libm's own error. The hard cases in `testdata/core-math.txt` and the special functions' cases in `testdata/mpmath.txt` carry correctly rounded results from mpmath, which `python testdata/references.py` writes. The special functions' f16 checks round rustymath's own f64 result, and the inverse incomplete functions recover each argument from its probability in `mpmath.txt`. The ported algorithms' notices are in `THIRD-PARTY.md`. The test data files carry their own. `links/`, which git ignores, holds shallow clones of the projects that tests and algorithms come from.

## Slice forms

`slice.rs` gives a function a second form for whole slices. The public traits are `Unary<T>`, `Binary<T>` and `Ternary<T>`, for functions of one, two and three items. Their methods take `&self`, so a function object can hold settings. `type Out` is the type of each result: the item type, unless the function gives another, such as a comparison's `bool`. `one` is the scalar form. `many` takes each argument as `Arg::One`, an item that pairs with every result, or `Arg::Many`, a slice. It appends the results to a `Vec`, and gives `false` where some item fails. `checked` is `one` with the same rule. A float or complex result fails where it is NaN and none of its arguments is, because rustymath gives NaN for an argument outside a function's domain. An integer result fails where it doesn't fit its type. A caller such as basedpl then takes another path for the whole call.

`forms!` writes a function object's forms as impls of the sealed trait `Forms<E, N>`, one for each item type it names. `forms!(Name at real: |k, [x, y]| body)` names f32 and f64. It also writes an f16 form, which converts `CHUNK` items at a time to f32, runs the f32 form and narrows its outputs. A list of types, as in `forms!(Abs at Complex<f32> => f32, Complex<f64> => f64: ...)`, names them directly. `=> T` makes each output a `T`. One macro, `arities!`, defines the three traits, each with a blanket impl at every item type that reaches `Forms`, so each method has one home. An object therefore implements `Unary<T>`, `Binary<T>` or `Ternary<T>` at each concrete type it has forms for, and nowhere else. Code that is generic over the float type states the bound it needs, as in `where Exp: Unary<F, Out = F>`. One object can have forms for several kinds of item, as `Exp` does for real and complex arrays. A body gives a value, an `Option` or a `Total`. The crate trait `Outcome` makes a value fail on NaN from non-NaN arguments, an `Option` fail on `None`, and a `Total` never fail. A body that never gives NaN from non-NaN arguments, such as `exp`'s or `hypot`'s, gives a `Total`. Its loop tests no item. A `functions!` entry marked `: total` wraps its body that way. The slice tests check each slice form's verdict against the NaN rule. A wrong mark fails them. A `functions!` entry marked `as`, such as `exp(x) in exp as Exp`, declares the object and calls `forms!`. An object whose forms differ from its free function, such as `Pow`, `Root`, `Sin`, `Cos` or `Tan`, is declared beside its code with its own `forms!` call and `many` body.

The forms compile in rustymath, and no caller inlines them. A caller's build settings can't change their loops, and an edit to a function's body rebuilds only rustymath. basedpl then relinks, in about 2 seconds for `pow`. A function object is a concrete type, never a generic one, because a generic object's forms would compile in each caller. A setting that chooses a loop, such as whether a tolerance is 0, is read once in a custom `many`, which then runs `each`.

`each` is the loop of the default slice form: an item body over `[Arg; N]`, with `Outcome`'s rule. It tests each output alone, one test for each item. Only where some output is NaN does a second pass check whether that item's arguments are NaN too, which reads the stored outputs and recomputes nothing. One and two arguments run through `pairs`, the loop over the pairings of items and slices, which writes into the result's spare capacity without zeroing it. That `unsafe` lives in `appended`. `two_pass` serves a function whose branch-free fast form misses rare items. `pow`'s and `root`'s fast form is `fast`, and sine's, cosine's and tangent's leave out arguments beyond their fast reduction. `two_pass` runs `CHUNK` items at a time. Its first pass writes NaN for each rare item and tests each result alone, as `each` does. A second pass over that chunk alone recomputes each NaN item with the function's form for any argument and checks it against its arguments. `split` serves a complex function whose formula combines real functions. It splits each `CHUNK` of complex items into slices of real and imaginary parts, computes the results' parts through real slice forms, then redoes with the scalar function each item that a test on its arguments and fast result picks. `CHUNK` is also how many items a caller converts or expands into buffers at a time.

Every slice form runs its loop through `each!`, `two_pass!` or `split!`. Each macro calls the function of the same name with every closure that runs on each item marked `#[inline(always)]`. The loops' own closures inside `each` and `two_pass` are marked too. LLVM leaves a large unmarked body out of line, and its call stops the loop vectorizing: `Sin.many` took 2.3 ns per item at f64 that way, against 0.87. A closure takes the attribute only where it is written, as a call argument. `pairs` itself stays `#[inline]`. Forcing it into basedpl's kernels slowed tolerant residue there by four times.

A closure's type comes from where it's written. Objects whose slice forms call one shared function with a runtime selector, such as which trig function to compute, get one loop between them, and that loop tests the selector on every item. Each such object writes its own closures, as `trig.rs`'s `objects!` does. Its loop then has the selector fixed.

## Reductions

`reduce.rs` holds sums, products, maximums and minimums of a contiguous slice, and their running versions. The trait `Reduction` gives each one, through `Sum`, `Product`, `Max` and `Min`: its unit, its step for one more item, its fold of a slice, its merge of the folds of two neighbouring runs, and its scan. Its `checked` is the step and whether the result fits. It defaults to the step, and integer sums and products override it. rustymath implements the trait once for each item type that each one takes. Code bounded by `Native` folds by any of the four with no further bound, through blanket impls over `F: Native`. The `f16` impls run the `f32` reductions and round each result once. `Sum` also takes complex numbers, adding their real parts and their imaginary parts. The free functions `sum`, `prod`, `max`, `min`, `extremes`, `cumsum`, `cumprod`, `cummax` and `cummin` call them. A fold keeps as many running results as `slice::running` gives in a local array, which vectorizes. That is 32, except for 16-byte results, such as complex sums, where 32 would fill every vector register, and 8-byte results in wasm, where LLVM leaves 32 in linear memory. Both of those keep 16. In wasm, 16-byte results keep 8, for the same reason. A float maximum or minimum is NaN where any item is NaN, as `maximum` and `minimum` are for two floats. `Core::maximum` computes one from a comparison and a select, which vectorizes on every target. The sealed trait `Extremes`, which `Native` requires, holds the folds of maximums and minimums and the step of their scans. On AArch64 they use the `fmax` and `fmin` instructions instead, which take one instruction where the comparison and select take four. Stable Rust reaches them only through `core::arch`, and a loop of those calls runs one item at a time. So the folds call the vector forms on 8 running vectors, and each step of a scan runs the scalar instruction. A scan takes groups of four, and only one operation in each group waits for the group before. A running maximum or minimum of integers goes through `records`. A block of 256 items whose fold leaves the running result unchanged repeats that result, and only the other blocks run the scan. The compiler vectorizes each block's fold because the block's length isn't fixed: a fold over a block of fixed length unrolls into one item at a time. An integer sum splits each 64-bit item into its high and low halves, which keeps it exact at `i64`. A signed running sum wraps. It gathers the sign bits that show overflow in one word, and tests that word once at the end. Integer products, and running sums of `u64`s, wrap through `Overflowing`, which also reports whether each one fits. The speed test compares each with the same taken item by item, in order.

Booleans fold by `Max` and `Min` as `or` and `and`, and by `Xor` and `Xnor` as not-equal and equal. Every Boolean scan, theirs included, runs through `Logical`, which holds a function of two Booleans as its truth table. For each value of the next item, the function maps the running result to itself, to its negation or to a constant. Where one value maps it to itself and the other to a constant, as for `or` and `and`, the results change at most once: `first_where` finds that place, and two runs fill the rest. Every other map is `r ↦ (s ∧ r) ≠ t` for two bits `s` and `t`, and two such maps compose into a third. A block of 64 items packs into a word of bits, through one multiplication for each 8 items. Its maps compose in six steps of shifts, and then apply to the running result, so only one step in each block waits for the block before. `SumAs<C>` counts the trues among Booleans, or sums integers, in the integer type `C`: a byte, `i16`, `i32` or `i64`. Its items implement `Term` and its totals `Tally`. Each step wraps, so the caller picks a type that holds every sum, which then comes out exact: basedpl bounds a running sum by the items' least and greatest values and the lane's length. A count sums the byte counts of chunks of 192 Booleans.

`Alternating` gives the right folds `x0 - (x1 - (x2 - …))` through `Sum`, and `x0 ÷ (x1 ÷ (x2 ÷ …))` through `Product`: the sum of the pairs' differences, or the product of their ratios. Floats and complex numbers go through `pairwise`, which runs `folded` on the pairs, so they combine the pairs in any order. Integers take the items at even positions less those at odd positions, through `alternated`, which keeps a running sum for each parity. On 16-bit items that measured about a third faster than `pairwise`, which must split each pair out of the vector lanes. `folded` and `alternated` share one loop, `running_results`. Integer sums run at `i32` for items of 16 bits or fewer, within runs of 2¹⁵ items, at `i64` within runs of 2³¹ items, and at `i128` for `i64` items. A quotient of floats doesn't fit where a running product or the result leaves the normal range. A product that underflows can come back with lost bits, so each step tests it. One that overflows stays infinite or turns NaN, which the test of the result catches. basedpl then folds item by item. `extremes` finds the least and the greatest items together in one pass, with one array of running minimums and one of maximums, because one array of pairs doesn't vectorize. `extremes_of` does the same through a key, which lets characters' `Key::range` read them as `u32`.

`along`, `fold_into` and `scan_along` fold and scan along the middle axis of an array of shape `[outer, len, inner]`, held row by row. A fold down the rows of a matrix has the shape `[1, rows, columns]`, and a fold along each row has `[rows, columns, 1]`. Where `inner` is 1, each lane is a contiguous slice, which goes through the fold or scan of a slice. A fold of rows of 1 to 15 items has a loop for each length instead, which the compiler unrolls: an image's 3 channels are an example. Where `inner` is more than 1, each row of items steps its row of totals by `checked`. `fold_into` folds the array a block at a time, for a caller that computes it in blocks, such as basedpl's fused folds. The fold of a lane's piece in one block merges with the lane's total by `merge`.

## Complex functions

`complex.rs` holds the complex functions, each generic over `R: Native` on `Complex<R>`. Their forms attach to the real functions' objects, such as `Exp` and `Pow`. Every function has one object, which serves each element type it makes sense for: `Sqrt` and the circle formulas `Sqrt1mx2`, `Sqrt1px2` and `Sqrtx2m1` live in `sqrts.rs`, `Abs`, `Sign` and `Angle` in `parts.rs`, and `Binom` comes from `functions!` with its real form in `special.rs`. `Abs` and `Angle` give real results for complex items. `Cis`, e^(iz), is the exponential of iz and takes reals too, giving complex results. On reals its slice form runs `Cos`'s and `Sin`'s, then makes the rare quarter turns exact, as `exp` does. Each function measures its error in ulps of the result's magnitude, not part by part. The scalar functions take |z| from `modulus`: `hypot` at f64, and at f32 the root of the sum of the squares in f64, which needs no scaling and is within half an ulp. The slice forms of `Exp`, `Ln`, `Pow`, `Sin`, `Cos`, `Sinh`, `Cosh` and complex `Cis` run through `split`, which on the Mac made them 1.2 to 2.5 times as fast at f64 and 1.7 to 3.8 times at f32. So do `Tan`, `Tanh`, `Asin`, `Acos`, `Atan`, `Asinh`, `Acosh`, `Atanh`, `Sqrt1mx2`, `Sqrt1px2` and `Sqrtx2m1`. Of those with speed rows, `Tan`, `Asin`, `Atanh` and `Sqrt1mx2` became 1.2 to 1.9 times as fast at f64 and 1.7 to 2.8 times at f32. The inverse functions and the `Sqrt` circle formulas take their square roots from `sqrt_parts`, which divides once for each item. Each split slice form sends the items its formula leaves out, such as tiny, infinite or huge parts, to the scalar form. `Abs`, `Angle` and `Sqrt` keep their loops over items, which ran faster than a split. The inverse circle and hyperbolic functions use Kahan's formulas over the complex square root. `atanh` takes each part from a formula that doesn't cancel. ln Γ uses Stirling's series, with the ten terms of `special::STIRLING`, where Re z or |Im z| is 7 or more, and the recurrence down from there. Below Re z = 0.1 it reflects, taking ln sin πz from its dominant exponential, which can't overflow. Its imaginary part follows the branch of SciPy's `loggamma`. `arc::atan2` gives the angles. The tests check every case in `testdata/complex.txt` at both widths, fused and unfused and through the split slice forms, plus C99's values on the branch cuts. `references.py` writes that file from mpmath.

## Number theory

`number_theory.rs` works on integers, so it doesn't use `functions!`. `Natural` is sealed by `Tier`, which gives each type its next narrower type: `u128` for `BigUint` and `u64` for `u128`. Each public function first moves its argument to the narrowest type that holds it, so small `BigUint` values compute at `u64` speed. `u64` and `u128` compute in Montgomery form, which `montgomery!` generates. `BigUint` uses plain residues and `modpow`. A narrowing call passes `check` on by value. Passing `&mut check` instead gives each level a new closure type, and the compiler never finishes instantiating the `u64` case. `Primes` keeps one byte for each 30 numbers, with a bit for each residue coprime to 30. It starts each segment from a copied pattern of the multiples of 7, and its segments double from 128 bytes to 32 KiB. The module's tests take a few hundredths of a second.

## Integers and random numbers

`integer.rs` holds functions of `i64`s that give `None` where the result isn't an `i64`: `gcd`, `lcm`, `binom`, `power` and `residue`. Their `i64` forms attach to the objects that floats and complex numbers use: `tolerant`'s `Gcd`, `Lcm` and `Residue`, whose integer forms ignore the tolerance they hold, and `Binom` and `Pow`. The `forms!` bodies return that `Option`. `Residue`'s slice form divides by a single divisor through `Divisor`, which multiplies and shifts, through `strength_reduce`, in place of a division instruction. `binom` of a negative n computes C(k + m, k) with m = -n - 1. `choose` takes as many steps as the smaller of k and n - k, and C(n, j) is at least 2^j while j is at most n/2, so it finishes or overflows within 64 steps. `encode` and `decode` give the digits of values in a mixed radix and the values of digits, as APL's `⊤` and `⊥` do. `polynomial::decode` gives the values of digits for floats.

`arith.rs` holds `Overflowing`, each integer type's `+`, `-`, `×` and magnitude with whether the result fits, in branch-free tests that vectorize. basedpl's exact integers use those flags to widen. The objects `Add`, `Subtract` and `Multiply`, and the integer forms of `Abs` and `Sign`, run `Overflowing` and keep its wrapped results, as NumPy's integer arrays do.

`random.rs` draws rolls and deals from a caller's generator. A roll with one bound for every item draws through one `Uniform` sampler.

## Exact numbers

`exact.rs` and `linalg/exact.rs` hold algorithms for exact numbers. They're generic over the integer type of a `num_rational::Ratio`, or over any `T: Clone + NumAssignRef`, which has the field operations by value and by reference. `BigRational` meets both bounds. Generic functions compile in each caller, unlike the function objects' forms. `exact.rs` gives `residue`, `gcd`, `lcm`, and `binom` with J's extension to a negative `k`. `linalg/exact.rs` reduces a matrix to reduced row echelon form, pivoting on the first nonzero item of each column, which is exact for exact numbers. `solve`, `pinv` and `determinant` build on it. A singular or wide matrix's least-norm solution goes through a rank factorization. `permanent` follows Ryser's formula, visiting the column subsets in Gray code order. `polynomial`'s `value`, `factored`, `from_roots` and `derivative` take the same types. basedpl runs these on exact rationals, and on `f64` and `Complex64` where its `Number` path holds floats or complex numbers. Each function that can run long has a `_with` version, whose check stops it, as in `number_theory`.

## Polynomials

`polynomial.rs` holds slice functions, so it doesn't use `functions!` either. `evaluate` runs Horner's rule on fixed blocks from `as_chunks_mut`, of as many items as `slice::running` gives, and pads the last partial block. With a variable length, a caller built with many codegen units, such as basedpl, calls `memcpy` and `Zip::new` once per block, and evaluation costs about three times as much. rustymath's speed test calls `evaluate` from a small crate of its own. Nobody has checked whether it shows this cost at basedpl's settings. Time a change in basedpl too. `roots` finds the eigenvalues of the companion matrix with `linalg::eigenvalues` in `f64`, through the real solver where every coefficient is real, and `fit` solves through `linalg::lstsq`.

## Search

`search.rs` and the slice functions in `tolerant.rs` came from basedpl, whose search, grade and sort call them. A slice holds at most `u32::MAX` items, because positions take 32 bits, and `index_of` and `tolerant::index_of` return them as `u32`s. `index_of` scans `x` once for each of up to `SCANNED` needles. Otherwise `index_of`, `classes` and `firsts` index keys in a table or a `foldhash` map. `counts` counts keys in such a table, and counts up to 4 keys in byte-wide lanes, one pass for each. `bins` gives each value the number of boundaries at or below it, from a table of those counts when the boundaries span one, and otherwise by a binary search that sixteen values take together. Grouping into two groups places both in one pass, writing 8 positions at a time for each group from a table of the set bits of each 8-bit mask. Tolerant searches index whole numbers when every float equals one below `whole_limit`. `wholes` finds those whole numbers a block at a time. basedpl also reads floats as integers through it, for counts and indices. A tolerant search with a nonzero tolerance otherwise files floats in `Near`'s buckets, and tolerant classification splits sorted order keys into runs. `Near` takes its bucket width from the tolerance and the float's epsilon, and a test compares it with a brute-force search at each width and at small and large tolerances. A tolerant comparison's slice form compares many items with one number through `Tolerant::range`. The functions that search, classify, count or sort a whole slice are `#[inline(never)]`, so each compiles as one function whatever calls it. Inlined into a caller's larger function, a loop's code changes whenever nearby code does. `Chains` walks a chain through `Links`, whose `next` stays small enough to inline into those loops. Time changes in basedpl, whose speed test has the search and grade cases.

`gather.rs` copies a slice's items into a buffer by position: cycling them, repeating each, keeping those a mask selects, taking them at indices and writing them at offsets. Each applies a conversion that the caller gives, so basedpl's `Gather` widens items as it copies them. `compress` skips each block of 64 counts that are all 0, copies each block that are all 1, and passes runs of mixed blocks to one pass that writes four places at a time. `⍸` and replicate by one in basedpl both use it.

## Linear algebra

`linalg.rs` holds inner products of row-major matrices. Each pair object, such as `PlusTimes`, implements `Inner<T>` at concrete item types, so its loops compile in rustymath, as slice forms do. A private `Pair` trait gives each pair's `g`, `f`, the identity of `f`, and its step, which is a fused multiply-add for `+.×`. `product` blocks the work as GotoBLAS and BLIS do. It packs a block of each argument into a buffer, and a micro-kernel computes a tile of the result in registers. The `tiles` module sets each target's tile shapes. The float pairs' micro-kernels run on explicit vectors on AArch64, in wasm with `simd128`, and on x86-64 with AVX2 and FMA. The `lanes!` macro writes them, from one line for each pair at each width. Elsewhere the micro-kernel is plain Rust. The SLP vectorizer packs a plain tile of at most 32 items, too few to keep the multiply-add units busy at f32. AVX2's maximum and minimum skip NaN, so its extremes compare and select as `Core::maximum` does. At `i64`, `+.×`, `⌈.+` and `⌊.+` run on the narrowest kernel that holds every value the product forms exactly: f32's where none exceeds 2^24 in magnitude, f64's where all lie below 2^51, and otherwise a plain kernel whose arithmetic wraps. `Inner::checked` gives `None` where a result could overflow, for callers such as basedpl that keep integers exact. The counts `PlusEqual` and `PlusNotEqual` count in the width of their items. Their explicit kernels, which `equalities!` writes, compare and subtract the all-ones mask from the count. `OrAnd` doesn't tile. It packs the rows of `b` 64 Booleans to a word. Each row of the result ORs together the packed rows that its row of `a` selects. `AndOr` runs the same loop with each input and each result negated, because `a∧.∨b` is `~(~a)∨.∧(~b)`. `PlusEqual` at `i64` counts at `i16` where `k` is below 2^15 and every item of both arguments lies in one window of 2^16 values, which it shifts into `i16`. Otherwise it counts at `i32` where every item fits. `PlusNotEqual` is `k` less `PlusEqual`.

`linalg/factor.rs` holds the decompositions of real and complex matrices: LU with partial pivoting, Cholesky, Householder QR and the SVD, with the solves, inverses and least-squares solutions built from them. The sealed trait `Factor` gives each one at `f32`, `f64` and `Complex` with parts of either type, and those implementations compile in rustymath. Free functions such as `lu` and `lstsq` call them. LU and Cholesky factor in blocks of an eighth of the rows, from 32 to 128 columns. QR's blocks take a sixteenth, from 32 to 64 columns. Those widths measured fastest on the Mac from 256 to 1024 rows. Each block factors in a transposed copy, where each column is contiguous. `linalg.rs`'s public `transpose_into` copies a block there and back in 8×8 tiles. LU and Cholesky halve a block's columns recursively, down to 16, and update the right half of each split with one matrix product. The rest of the matrix updates through the `+.×` kernels, which `Tiled::add_product` reaches with arguments read through closures and a result whose rows are strided. Cholesky's update skips the tiles above the diagonal. QR keeps each block's reflections in the WY form `I - V T Vᴴ`, as a `Block`. `Block::apply` applies a block, or its adjoint, to any matrix: QR's update of the columns after each block, `Reflections::q`, `Reflections::apply`, and `Reflections::apply_adjoint` above `FEW_COLUMNS` right-hand sides. The triangular solves behind `Lu::solve` and `Lu::inverse` substitute 32 rows at a time with vector operations, then remove those rows from the rest with one matrix product. `lstsq` reflects `b` to `Qᴴ b` without forming Q, then solves through the SVD of R. `solve` and `pinv` use LU while every pivot exceeds ε × n × the largest magnitude. Otherwise they take the least-norm path through the SVD, with NumPy's cutoff. `rank` counts the singular values above that cutoff, which the `cutoff` helper computes for both. `Lu::lower` and `Lu::upper` give L and U as square matrices. `qr_complete` forms all m columns of Q. `Lu::log_determinant` gives the determinant's sign and the logarithm of its magnitude, which can't overflow.

`linalg/scalar.rs` holds `Scalar`, the public sealed trait of the item types the decompositions take: `f32`, `f64`, and `Complex` with parts of either type. A blanket implementation covers every `Native` float with the plain operations, and at a real type the generic code performs the same arithmetic as the real code it replaced. `Scalar`'s method names, such as `mul_acc`, `reciprocal` and `abs1`, differ from those of `num_traits::Float` and `Core`. Calls in code bounded by `Native` then stay unambiguous. A complex quotient follows Smith's algorithm, which doesn't overflow where `divide`'s faster formula does. LU, Cholesky, QR, the SVD and the Hermitian eigen problem are generic over `Scalar`. A complex Cholesky gives L Lᴴ. A complex QR's reflections, as LAPACK's `zlarfg` makes them, leave R with a real diagonal. `Tiled` gives `Complex` four real products of the parts, each on the real kernels. `Factor` and the public functions take all four types. Singular values and a Hermitian matrix's eigenvalues have the parts' type, `Scalar::Real`, and `Eig` holds complex numbers with parts of that type. Singular vectors and eigenvectors have no chosen sign or phase.

`linalg/factor/eigen.rs`, a child module that shares `factor.rs`'s private helpers, solves the symmetric and Hermitian eigen problems. `eigh` reads a matrix's lower triangle into the upper triangle of a transposed copy, whose rows are contiguous. Householder reflections reduce it to a real tridiagonal matrix. A Hermitian matrix's reduction conjugates wherever it reads a row of the upper triangle as the column below the diagonal. Each reflection's single pass over the rows below it applies its rank-two update and accumulates the next reflection's product with that matrix, as faer's `tridiag_fused_op` does. `reflections` forms Qᵀ one reflection at a time up to 96 rows. Above that, `Reflections::q` forms it in the WY form, because those reflections have the layout of a QR factorization's without the first row and column. `general.rs` and `svd.rs` use it too. Up to 64 rows, `eigh` runs implicit QL iterations, as EISPACK's `tql2` runs them, rotating pairs of rows of Qᵀ into Vᵀ. Larger tridiagonal matrices go to divide and conquer. Each half of the matrix is solved recursively. The merge deflates small items and near-equal eigenvalues, then finds each remaining root with `secular.rs`'s root finder. Rebuilding z from the computed roots, as Gu and Eisenstat do, keeps the eigenvectors orthogonal. The merged eigenvectors come from the tiled product, and the reflections apply to them directly, without forming Qᵀ. Eigenvalues alone take implicit QL without rotations, at any size. A NaN never counts as negligible, so a matrix holding one runs out of iterations and gives `None`.

`linalg/factor/general.rs`, another child module, solves the general eigen problem, as LAPACK's `dgehd2`, `dlahqr` and `dtrevc` do for real matrices, and `zgehd2`, `zlahqr` and `ztrevc` for complex ones. Householder reflections reduce the matrix to upper Hessenberg form. `eigen.rs`'s `reflections` forms their Qᵀ. QR iterations then reduce the Hessenberg matrix to Schur form, accumulating Zᵀ in the rows of Qᵀ. Francis double-shift iterations leave a real matrix's Schur form quasi-triangular. Single-shift iterations leave a complex matrix's Schur form triangular, after unit scalings make each subdiagonal item real. `eigenvalues` skips Zᵀ. Its iterations then transform only the active block. Back substitution in the Schur form gives its eigenvectors. One product with Z turns them into the matrix's own. Each eigenvector has unit length. A trait, `Schur`, holds the steps that differ between real and complex matrices: the iterations, the back substitution and the unit scaling. `eig_factor` runs the rest for both. The working copy of the Hessenberg matrix pads each row by 8 items. The iterations' reflections from the right read down its columns. With rows of 256 items, a column's items all fell in a few cache sets, and the iterations ran 3 times slower. `standard`, a port of LAPACK's `dlanv2`, compares a quantity in the matrix's own units with 4ε. A matrix scaled by a power of two therefore gives exactly scaled results only where `safe_scale` brings both copies to the same matrix.

`linalg/factor/svd.rs`, another child module, computes the SVD as LAPACK's `dgebrd`, `dorgbr`, `dbdsqr` and `dbdsdc` do. Householder reflections from the left and the right reduce the matrix to real upper bidiagonal form, in one pass over the rows below each step's row. Each right reflection of a complex matrix maps the conjugate of its row, as in LAPACK's `zgebrd`. The pass applies both of the step's reflections to each row, then adds the row's part of the next step's `vᴴ A`. Up to 64 columns, and for singular values alone, QR's `Reflections` forms Uᵀ from the left reflections, and `eigen.rs`'s `reflections` forms Vᵀ from the right ones, which have the layout of the tridiagonal reduction's. Golub-Kahan QR sweeps with a Wilkinson shift then drive the superdiagonal to zero, rotating pairs of rows of Uᵀ and Vᵀ. Above 64 columns, with vectors, divide and conquer gives the bidiagonal matrix's singular vectors, following faer's `bidiag_svd.rs`. It splits an (n+1)×n lower bidiagonal matrix at its middle column, solves each half, and merges the halves through an arrow matrix whose singular values `secular::root` finds. The reflections then apply to those vectors without forming Q. On the Mac, that took a 512×512 SVD from 82 ms to 52 ms, and a 1,024×1,024 one from 590 ms to 357 ms. A matrix more than 11/6 times as tall as it is wide first reduces to the R of its QR factorization, and `Reflections::apply` multiplies R's U by Q. A matrix holding a NaN or an infinity gives NaN for every result. `Svd::pseudoinverse` forms V Σ⁺ Uᵀ directly.

The speed test times `+.×` and each decomposition in copies of its matrix's items: real matrices at 256×256, complex ones at 128×128, and `lstsq`'s at 4096×16. Their budgets are four times their Mac cost until CI measures them. The last comparisons with faer were measured on the Mac, before faer left rustymath and basedpl. The f64 LU solve, inverse, Cholesky and QR took 1.2 to 1.4 times faer's time, and the f32 ones 1.4 to 1.8 times. `lstsq` took about 0.6 times at both widths. At 256 rows, `eig` took about 1.2 times faer's time, and `eigenvalues` about the same. faer chases many bulges at once and deflates eigenvalues early, where `general.rs` chases one double-shift bulge at a time. Singular values alone took 0.55 to 0.7 times faer's time on square matrices, and tall SVDs 1.2 to 1.4 times. Divide and conquer came after the last comparison, for `eigh` and the SVD above 64 rows. Scaling the earlier ratios by its gains gives `eigh` about 0.7 times faer's time at 256 rows and 0.85 times at 512, and the square SVD about 0.75 times at 256 and 0.8 times at 512. Nobody has measured those against faer.

## Versioning

The canonical version lives in `[workspace.package]` in `Cargo.toml`, which both crates inherit. `pyproject.toml` gets the Python package version from Cargo via `dynamic = ["version"]`.

## Build profiles

The profiles match basedpl's line for line. Cargo ignores a dependency's own profiles. Inside basedpl, rustymath compiles at basedpl's settings. With the same settings here, the speed test times code compiled the way basedpl compiles it. Change both `Cargo.toml` files together.

`release` compiles at opt-level 2, incrementally and without LTO, into Cargo's default of 256 codegen units. `cargo test` and `cargo develop` share the `test` profile, which inherits `release`. `cargo develop` installs the extension from that build into the editable package. Editable installs through `uv sync` or `pip install -e` compile no Rust, because the build backend is `fastws.build_backend`. In CI, `cargo develop` runs after `cargo test` in the same job and reuses its build. Don't use `maturin develop`. It compiles a second copy of the crate, unoptimized unless given `--release`.

The `Release` workflow builds distributed wheels with `dist`. It turns incremental compilation off and strips the result. Without incremental compilation, Cargo uses 16 codegen units, with thin LTO across them.

## Release

1. Run `cargo develop && pytest -q`.
2. Confirm the release version in `Cargo.toml` (`[workspace.package].version`).
3. Run `ship-release`.

`ship-release` pushes a `v<version>` tag, which starts the `Release` workflow, in `ci.yml`, then bumps the version.
