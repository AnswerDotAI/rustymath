# The budgets that `test_speed.py` checks, for rustymath's Python API. Each section starts with an item type in brackets. Each line under it holds a Python expression and its two native budgets, separated by tabs: first for macOS on Apple silicon, where matrix products and decompositions run on Accelerate, then for Linux on CI's x86 runner, where they run on rustymath's own kernels. `rm.timing().column` picks the budget a machine checks. The expression names the arrays that `test_speed.py` makes. A budget counts copies of 65,536 items of the section's type, the number of items in each case's main input.
# A budget is the case's expected cost times the multiplier that `rustymath_timing::budget` holds, as basedpl's DEV.md describes, and at least 0.5. A line such as `# held linux 14.2: REASON` above a case's line holds that column at the budget for the cost it gives, until the gap it names is fixed, and `# busy` does the same for CI's busy hosts, as `rustymath_timing::hold` reads them. The expected cost starts from a first-principles analysis of what the case should cost. A later expected cost comes from a fuller understanding of the case than that analysis gives, such as a platform difference or a cost the analysis missed. A comment above each case, or above its group, gives the expected cost and its reason, as in "1 copy: one read and one write per item", and records each later change with its reason.
# One expected cost serves both platforms at first. A platform's budget differs only where a specific difference on that platform is found, such as Accelerate's matrix products on macOS.
# A case that costs more than its budget needs study, which finds either a speed bug to fix or something the analysis missed. Avoid raising a budget to match a run without understanding why the case costs what it does.
# After its budgets, a case's line can record the instructions that it retires for each item in one more tab-separated field, as `rustymath_timing::count` reads it, such as `instructions linux 41.5`. `test_speed.py` fails a count more than `rustymath_timing::COUNT_MARGIN` times its record. `basedpl.bpltests.set_counts` writes the counts from a calibration run's log.
